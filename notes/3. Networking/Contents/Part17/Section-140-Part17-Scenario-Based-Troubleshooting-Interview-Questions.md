# Section 140 (Part 17): Scenario-Based Troubleshooting Interview Questions

## 1. Scenario Bank: Connectivity and Reachability Failures

**Scenario 1.** "A host can't reach a service in another subnet at all — not even a ping response." Walk through your diagnosis.
**Model answer:** I'd start with the OSI-layer walkthrough ([§115](../Part14/Section-115-Part14-A-Systematic-Troubleshooting-Methodology-OSI-Layer-Walkthrough.md)) rather than guessing: confirm the local interface is up (`ip link show`), confirm a route exists to the destination (`ip route get <dest>`), and only then test reachability (`ping -c 4`). If the route lookup itself fails or points somewhere unexpected, the problem is Layer 3 routing, not connectivity at all — no point testing further up the stack. If a route exists and ping still fails, I'd check whether ICMP itself is being filtered (common in cloud security-group defaults) before assuming the host is actually unreachable, and corroborate with a port-level test (`nc -zv`) against the actual service port ([§116](../Part14/Section-116-Part14-Connectivity-Testing-ping-traceroute-tracert-mtr.md), [§117](../Part14/Section-117-Part14-Port-and-Service-Testing-telnet-nc-curl-for-Network-Diagnostics.md)).

**Scenario 2.** "`nc -zv` against a specific port hangs for 30 seconds and then times out, with no error." What does this tell you, and what's different about a case where it returns `Connection refused` instantly?
**Model answer:** A hang-then-timeout with no response at all typically means a firewall or security group is silently *dropping* the SYN — no RST is generated, so the client just retransmits until it gives up. An instant `Connection refused` means the packet reached the host and its TCP stack actively replied with an RST, because the port is genuinely closed (no listener) rather than filtered. These point to different fixes: a firewall/security-group rule change for the timeout case, versus starting or fixing the target service for the refused case ([§55](../Part7/Section-55-Part7-TCP-Three-Way-Handshake-and-Connection-Teardown-FIN-RST.md), [§117](../Part14/Section-117-Part14-Port-and-Service-Testing-telnet-nc-curl-for-Network-Diagnostics.md)).

**Scenario 3.** "A newly deployed pod in Kubernetes can't reach another pod in a different namespace, but pods within the same namespace can reach each other fine." What's your hypothesis and first checks?
**Model answer:** Intra-namespace connectivity working while cross-namespace fails points toward a NetworkPolicy or CNI-level segmentation rule scoping traffic by namespace, rather than a broader cluster networking failure (a broader CNI failure would typically also break same-namespace traffic). I'd check for NetworkPolicy resources restricting ingress/egress by namespace selector, confirm the CNI plugin ([§112](../Part13/Section-112-Part13-CNI-Plugins-Conceptual-Overview.md)) is healthy cluster-wide, and use a debug pod to test connectivity directly with `curl`/`nc` before assuming the application code itself is at fault.

**Scenario 4.** "Users report a website is unreachable, but your own monitoring shows the origin server healthy and serving traffic normally." How do you reconcile this?
**Model answer:** This mismatch between "origin healthy" and "users can't reach it" points toward something between the user and the origin — DNS resolving to a stale or wrong IP, a CDN/edge issue, a regional ISP or routing problem affecting only some users, or a client-side DNS cache issue. I'd first verify DNS resolution from an external, uninvolved vantage point (`dig @8.8.8.8`) against what the origin/CDN actually expects, then check whether the affected users share a common ISP, region, or resolver — a pattern that would point at a path-specific or DNS-propagation issue rather than the origin itself ([§120](../Part14/Section-120-Part14-DNS-Troubleshooting-Workflows.md), [§123](../Part14/Section-123-Part14-Common-Failure-Scenarios-and-Root-Cause-Case-Studies.md) §5.1).

## 2. Scenario Bank: Performance, Intermittent, and Load-Dependent Failures

**Scenario 5.** "An SSH session connects and lets you type commands, but hangs completely the moment a command produces large output (like `ls` on a big directory)." Diagnose this.
**Model answer:** This exact "small packets fine, large packets hang" signature is the classic fingerprint of an MTU/Path MTU Discovery black hole — most likely a firewall somewhere on the path is blocking the ICMP "Fragmentation Needed" messages PMTUD depends on, so oversized packets are silently dropped with no error ever reaching the sender. I'd confirm with a size-bisected `ping -M do -s` test and `tracepath`, and the fix is almost always enabling MSS clamping on the relevant gateway (VPN, tunnel, or overlay) or permitting the specific ICMP type through the blocking firewall ([§122](../Part14/Section-122-Part14-MTU-Issues-and-Path-MTU-Discovery.md)).

**Scenario 6.** "A service works fine most of the day but every night during a batch job, several unrelated services start seeing connection timeouts to a shared database." What do you check first?
**Model answer:** A time-correlated, load-triggered pattern affecting multiple otherwise-unrelated consumers of a shared resource points at resource exhaustion on that shared resource rather than a bug in any individual service. I'd check the database's own connection limits and the state of any NAT gateway or proxy sitting in front of it (`conntrack` table occupancy, `nf_conntrack_count` vs `max`), since a batch job opening many concurrent connections is a textbook trigger for connection-tracking-table or connection-pool exhaustion, a distinct failure mode from a simple bandwidth bottleneck ([§82](../Part10/Section-82-Part10-Firewall-Fundamentals-Stateless-vs-Stateful-Filtering.md), [§20](../Part3/Section-20-Part3-NAT-and-PAT-Concepts-and-Real-World-Use.md)).

**Scenario 7.** "Customers on one specific ISP report the API is slow, while everyone else reports normal performance." How do you investigate a segment-specific complaint like this?
**Model answer:** A segment-specific complaint is by definition invisible from an internal, unaffected vantage point — I would not conclude "everything looks fine" from testing on our own network. I'd run `mtr` toward the API host from (or as close as possible to) the affected ISP's actual path, looking for packet loss or latency spikes at a specific hop, and independently test for a reduced path MTU with `ping -M do -s`, since a partner VPN or peering link on that specific path is a common, fixable cause of exactly this kind of segment-specific degradation ([§121](../Part14/Section-121-Part14-Routing-and-Path-Troubleshooting-Asymmetric-Routing-Route-Leaks.md), [§123](../Part14/Section-123-Part14-Common-Failure-Scenarios-and-Root-Cause-Case-Studies.md) §5.1).

**Scenario 8.** "A backend server's health checks intermittently fail from the load balancer, but a manual `curl` from an engineer's laptop to the same backend always succeeds." What's the key clue, and how do you confirm the root cause?
**Model answer:** The key clue is that two different sources get different results against the identical backend — that rules out the backend or the health-check configuration being broken in general, and points at something specific to the load balancer's source (IP/subnet). I'd capture traffic on the backend filtered to the load balancer's actual source IP during a health-check attempt; if its SYNs go unanswered while the manual test succeeds, a security-group/firewall rule is permitting the engineer's broader IP range but excluding the load balancer's specific source range ([§84](../Part10/Section-84-Part10-Security-Groups-vs-Network-ACLs-Cloud-Agnostic-Concepts.md), [§123](../Part14/Section-123-Part14-Common-Failure-Scenarios-and-Root-Cause-Case-Studies.md) §5.2).

**Scenario 9.** "After migrating a service behind a new VPN gateway, TLS handshakes complete but bulk file transfers over the same connections consistently stall." What do you suspect, and why specifically after this migration?
**Model answer:** Same MTU/PMTUD black-hole signature as Scenario 5, but the "after this migration" detail is the important clue: the new VPN tunnel's encapsulation overhead reduced the effective MTU available to the original payload, and if MSS clamping wasn't configured on the new gateway, TCP still negotiates based on each side's *local* interface MTU, missing the smaller MTU actually available mid-path. I'd verify the tunnel interface's configured MTU against its actual encapsulation overhead and enable MSS clamping as the durable fix, rather than relying on PMTUD's fragile ICMP-dependent fallback ([§92](../Part11/Section-92-Part11-IPsec-AH-ESP-Tunnel-vs-Transport-Mode-IKE-Phases.md), [§94](../Part11/Section-94-Part11-WireGuard-Design-Philosophy-and-Key-Concepts.md), [§122](../Part14/Section-122-Part14-MTU-Issues-and-Path-MTU-Discovery.md)).

**Scenario 14.** "A container platform's pods can reach external internet addresses fine, but two pods on the same node in different namespaces intermittently fail to reach each other, and restarting the CNI plugin's pod temporarily fixes it." What's your hypothesis?
**Model answer:** External connectivity working while intra-cluster, cross-namespace connectivity is intermittently broken points at the CNI plugin's own internal state (its route/overlay table, or its per-node agent) rather than the underlying physical network, since a genuine physical or routing fault would be far more likely to also disrupt the external path. The fact that restarting the CNI agent pod "fixes" it temporarily is itself evidence pointing at stale or corrupted internal state in that specific component rather than a persistent, externally-caused fault. I'd check the CNI agent's own logs for errors around the time of failure, verify Kubernetes NetworkPolicy resources aren't intermittently misapplied, and treat a recurring need to restart the CNI agent as a bug to root-cause (likely a resource leak or a race condition in its state reconciliation) rather than a routine operational workaround ([§110](../Part13/Section-110-Part13-Container-Networking-Fundamentals-Bridge-Host-and-Overlay-Modes.md)-[§112](../Part13/Section-112-Part13-CNI-Plugins-Conceptual-Overview.md)).

**Scenario 15.** "A monitoring dashboard shows a load balancer's active connection count climbing steadily over several days with no corresponding increase in real traffic, eventually degrading performance." Diagnose.
**Model answer:** A connection count climbing independently of actual traffic volume strongly suggests a connection leak rather than genuine load — either backend connections that are opened but never properly closed (a CLOSE_WAIT-style application bug, [§61](../Part7/Section-61-Part7-Connection-States-and-the-TCP-State-Machine-LISTEN-ESTABLISHED-TIME-WAIT.md)), or a load-balancer/proxy configuration issue holding idle connections open far longer than necessary. I'd check the state breakdown of those connections (`ss -tan` state counts on the load balancer or backend, if accessible) specifically looking for an abnormal and growing CLOSE_WAIT or ESTABLISHED-but-idle count, and correlate the growth rate against recent deploys, since a newly introduced code path failing to close connections on an error branch is a very common root cause of exactly this slow, steady climb.

## 3. Prerequisites and Dependencies

This section assumes full familiarity with the OSI-layer troubleshooting methodology ([§115](../Part14/Section-115-Part14-A-Systematic-Troubleshooting-Methodology-OSI-Layer-Walkthrough.md)) and every diagnostic tool covered across Part 14 ([§116](../Part14/Section-116-Part14-Connectivity-Testing-ping-traceroute-tracert-mtr.md)-[§123](../Part14/Section-123-Part14-Common-Failure-Scenarios-and-Root-Cause-Case-Studies.md)) — `ping`/`traceroute`/`mtr` ([§116](../Part14/Section-116-Part14-Connectivity-Testing-ping-traceroute-tracert-mtr.md)), `nc`/`curl` ([§117](../Part14/Section-117-Part14-Port-and-Service-Testing-telnet-nc-curl-for-Network-Diagnostics.md)), `tcpdump`/Wireshark ([§118](../Part14/Section-118-Part14-Packet-Capture-Fundamentals-tcpdump-Basics.md)-[§119](../Part14/Section-119-Part14-Deeper-Packet-Analysis-Wireshark-Concepts-and-Filters.md)), DNS workflows ([§120](../Part14/Section-120-Part14-DNS-Troubleshooting-Workflows.md)), routing/path diagnostics ([§121](../Part14/Section-121-Part14-Routing-and-Path-Troubleshooting-Asymmetric-Routing-Route-Leaks.md)), and MTU/PMTUD ([§122](../Part14/Section-122-Part14-MTU-Issues-and-Path-MTU-Discovery.md)) — since every scenario below is deliberately built to require applying two or more of those tools in sequence, exactly as [§123](../Part14/Section-123-Part14-Common-Failure-Scenarios-and-Root-Cause-Case-Studies.md)'s case studies modeled. It also draws on load balancing (Part 9), firewall/security-group behavior (Part 10), and TCP mechanics (Part 7) as the domains most scenarios ultimately resolve into.

## 4. Architecture / Conceptual Diagram

```text
   THE SCENARIO-ANSWERING PATTERN USED THROUGHOUT THIS SECTION

   1. Restate the symptom precisely — what exactly fails, for whom,
      under what condition (always / intermittent / load-triggered)?
              │
              ▼
   2. Identify the DISCRIMINATING CLUE in the symptom itself —
      e.g. "small packets work, large ones don't" → MTU
           "two sources get different results" → source-specific rule
           "one segment affected, others fine" → path-specific issue
              │
              ▼
   3. Pick the tool(s) that would confirm or rule out that specific
      hypothesis — never jump straight to a fix without evidence
              │
              ▼
   4. State the confirming evidence AND the specific remediation —
      a good interview answer never stops at "I'd investigate X,"
      it names what result would confirm X and what the fix is
```

- Every scenario in sections 1-2 is deliberately built around one sharp discriminating clue — training yourself to spot that clue quickly (rather than starting an unstructured investigation from scratch) is the actual skill this section drills.
- Notice that almost none of the model answers above introduce a new tool beyond Part 14's existing toolkit — the skill being tested is *sequencing and interpretation* of familiar tools against an unfamiliar symptom, not knowledge of exotic techniques.

## 5. Scenario Bank: DNS, TLS, and Multi-Layer Ambiguous Failures

**Scenario 10.** "A user insists 'it's a DNS problem' because the site doesn't load, but `dig` shows DNS resolving correctly to the expected IP." How do you proceed?
**Model answer:** I would not accept the user's inferred cause at face value — an accurate symptom report ("the site doesn't load") frequently comes bundled with an incorrect diagnosis. Since DNS is independently confirmed healthy, I'd move up the stack: test basic connectivity and the specific port, then check the TLS handshake with `curl -v` or `openssl s_client`. A very common root cause fitting this exact pattern is an expired TLS certificate — the connection reaches the server fine but the handshake fails, which a user experiencing "the site won't load" easily misattributes to DNS ([§65](../Part8/Section-65-Part8-TLS-SSL-Fundamentals-Handshake-Certificates-Cipher-Suites.md), [§123](../Part14/Section-123-Part14-Common-Failure-Scenarios-and-Root-Cause-Case-Studies.md) §5.3).

**Scenario 11.** "A DNS record was changed an hour ago, but some users still see the old IP address." Is this a bug?
**Model answer:** Not necessarily — this is very likely expected TTL-driven caching behavior. I'd check the record's configured TTL; if it was, say, 3600 seconds, seeing stale answers for up to an hour after the change is completely normal, not a fault. I'd confirm by querying the authoritative name server directly (bypassing every cache) to verify the *source of truth* is correct — if it is, the fix is simply waiting out the TTL, or lowering TTLs proactively before future planned changes ([§120](../Part14/Section-120-Part14-DNS-Troubleshooting-Workflows.md)).

**Scenario 12.** "An internal service name resolves to a private IP from inside the VPC, but fails to resolve at all from an external partner's network — and the partner is asking if this is a bug." How do you respond?
**Model answer:** Before treating this as a bug, I'd confirm whether the name is intentionally internal-only (split-horizon DNS design) — if so, the external failure is expected and correct, and the partner needs a different, deliberately public-facing endpoint rather than a DNS "fix." If the name was actually meant to resolve externally too, I'd compare internal resolution against an external public-resolver query to see what the outside world actually gets, and check whether only the private/internal DNS zone was updated while the public zone was never touched — a common real cause ([§50](../Part6/Section-50-Part6-Split-Horizon-Split-View-DNS.md), [§120](../Part14/Section-120-Part14-DNS-Troubleshooting-Workflows.md)).

**Scenario 13.** "A team migrating to IPv6 dual-stack reports that their service works over IPv4 but is unreachable over IPv6 for a subset of external users, with no clear pattern." What's the likely mechanism, and how do you validate it?
**Model answer:** This is a strong candidate for an incomplete dual-stack rollout masked by Happy Eyeballs (RFC 8305) — most modern clients race IPv4 and IPv6 connection attempts and silently prefer whichever succeeds, so a broken or partially configured IPv6 path (missing firewall rule, incomplete routing, incorrect AAAA record) doesn't cause an outright failure for most users, just extra latency from IPv4 fallback — except for users or networks where IPv4 fallback is itself constrained, where the same gap manifests as an outright failure instead of delay. I'd test explicitly over IPv6-only (`curl -6`, or forcing IPv6 resolution) independent of any fallback, and audit firewall/security-group rules and DNS AAAA records specifically for IPv6 parity with the IPv4-side configuration ([§22](../Part3/Section-22-Part3-IPv6-Subnetting-and-Dual-Stack-Coexistence.md)).

**Scenario 16.** "A newly peered VPC can reach a third VPC's resources through a shared hub, but two directly-peered VPCs (no hub involved) cannot reach each other at all, despite both peering connections individually showing 'active.'" What's the likely design gap?
**Model answer:** This is very likely a route-table gap rather than a peering-connection problem — a peering connection being "active" only means the logical relationship exists; each side's route table must still explicitly include a route to the peer's CIDR through that peering connection, and it's easy to configure the peering connection itself correctly while forgetting to add or update the corresponding route table entries on one or both sides. I'd check both VPCs' route tables directly for an explicit route to the other's CIDR via the peering connection ID, rather than assuming the peering connection's "active" status implies routing is also correctly configured ([§103](../Part12/Section-103-Part12-VPC-VNet-Peering-and-Transitive-Routing-Limitations.md)).

## 6. Production Usage Notes

- Real interviewers frequently withhold detail deliberately and reward candidates who *ask clarifying questions* before diagnosing — "is this affecting one user or everyone," "since when," "is it constant or intermittent" are the same questions a real on-call engineer asks first, and demonstrating that instinct matters as much as the eventual technical answer.
- A strong scenario answer names both the confirming evidence and the specific remediation — stopping at "I'd investigate the firewall" without saying what a positive/negative result would look like reads as less rigorous than completing the loop.
- When practicing these scenarios, time yourself — real technical interviews are time-boxed, and the actual skill being assessed includes reaching a structured hypothesis quickly, not just eventually.

## 7. Security Considerations

- Several scenarios above (asymmetric routing bypassing a firewall, a security-group rule permitting a broader source range than intended) are simultaneously operational incidents and security-relevant findings — a strong answer flags both angles rather than treating the scenario as purely a connectivity puzzle.
- Diagnostic techniques used to answer these scenarios (packet capture, port scanning) carry their own handling requirements in a real environment — a candidate who mentions "I'd also make sure this capture is handled per our data-sensitivity policy" signals production maturity beyond pure technical correctness.
- Scenario 10's expired-certificate root cause is itself a security lapse, not merely an availability one — a strong answer notes that repeated certificate-expiry incidents erode users' trust in legitimate certificate warnings generally, not just that one incident's downtime.

## 9. Best Practices

- Always restate the scenario back in your own words before diagnosing, out loud in an interview — this confirms you've understood the actual symptom and buys a moment to structure your approach.
- Name the specific tool and the specific expected output at each diagnostic step, rather than speaking in generalities ("I'd check the network") — specificity is what distinguishes a strong scenario answer from a vague one.
- Practice scenarios out of a random order, not in the sequence presented here — real interviews don't telegraph which category (MTU, DNS, load-dependent) a scenario belongs to, and part of the skill is recognizing the category from the symptom alone.
- After answering, explicitly state what you'd do to prevent recurrence, not just how you'd fix the immediate incident — this is a consistently rewarded signal at Senior/Architect interview tiers.

## 10. Common Anti-Patterns / Mistakes

- **Jumping straight to a single guessed root cause without stating what evidence would confirm or rule it out.** A confident-sounding guess that turns out wrong reads worse than a structured, evidence-based approach that takes a beat longer to reach the same conclusion.
- **Ignoring the discriminating clue in the scenario's phrasing.** Interview scenarios are usually worded precisely (e.g., "small packets fine, large ones fail") specifically because that phrasing is the clue — treating it as incidental detail rather than the key signal wastes the most valuable information already given.
- **Fixing the immediate symptom in the answer without addressing why it happened.** "I'd renew the certificate" is an incomplete answer to Scenario 10 without also mentioning fixing the renewal automation that should have prevented the expiry in the first place.

## 11. Interview Questions

**🎯 Beginner:** _"A user says they can't reach a website. What are the first three things you'd check?"_
**Model answer:** First, scope the problem — is it just this user or everyone, and has it always failed or did it recently break? Then check DNS resolution (`dig`) to confirm the hostname resolves to the expected IP. Then check basic connectivity and the specific port (`ping`, then `nc -zv` or `curl -v` on the actual service port) before assuming a network-wide outage.
_What the interviewer is probing for:_ Basic structured triage instinct rather than guessing.

**🎯 Intermediate:** _"How do you decide which diagnostic tool to reach for first, given an unfamiliar symptom?"_
**Model answer:** I let the symptom pick the layer. A single-hostname failure while everything else works points toward DNS or TLS, so I'd start near the top of the stack. "Everything is unreachable" points toward something foundational, so I'd start at Layer 1-3. If the symptom is genuinely ambiguous, I default to the systematic bottom-up OSI walkthrough, since a lower-layer failure always masks everything built on top of it.
_What the interviewer is probing for:_ Adaptive, symptom-driven tool selection rather than rigid, one-size-fits-all triage.

**🎯 Senior:** _"Describe the most difficult networking incident you've diagnosed, or, if hypothetical, what would make a networking incident genuinely hard to diagnose?"_
**Model answer:** The hardest incidents share a common shape: the reported symptom is accurate but the reporter's inferred cause is wrong, and the actual root cause is silent rather than error-producing — a PMTUD black hole (no error, just a hang) or a firewall rule that permits one source but not another (works "for me," fails for the actual affected system) are both examples. What makes them hard isn't tool unfamiliarity, it's that the natural first hypothesis (based on the reported symptom) points in the wrong direction, and disciplined, evidence-gathering troubleshooting — rather than trusting the initial framing — is what eventually surfaces the real cause.
_What the interviewer is probing for:_ Genuine incident-response experience or, for a hypothetical answer, mature understanding of what actually makes troubleshooting hard (silent failures and misleading framing, not tool obscurity).

**🎯 Architect:** _"How would you build a team's collective troubleshooting capability so incident resolution doesn't depend on a few senior individuals' pattern-matching?"_
**Model answer:** I'd formalize the layered methodology and this kind of scenario-based training as an actual onboarding and ongoing-practice artifact, not tribal knowledge — new engineers should drill scenarios like these explicitly, not absorb the pattern-matching only by living through enough real incidents. I'd pair that with always-available diagnostic infrastructure (rolling packet captures, synthetic monitoring for DNS/TLS/connectivity) so the evidence needed for common patterns is available immediately during a real incident rather than requiring ad hoc setup. I'd track "time to correct hypothesis" as an explicit postmortem metric, since chasing the wrong initial hypothesis (as in several scenarios above) is the single biggest driver of long incident resolution times, and I'd convert every non-trivial resolved incident into a documented symptom-to-diagnosis pattern that compounds the team's capability over time.
_What the interviewer is probing for:_ Organizational, scalable thinking about troubleshooting capability, not just personal diagnostic skill.

## 12. Common Misconceptions

1. **"A scenario-based question is testing tool knowledge."** It's testing sequencing and interpretation of already-known tools against an unfamiliar symptom — the tools themselves (`ping`, `curl`, `tcpdump`, `dig`) are rarely novel; the skill is applying them in the right order and reading their output correctly.
2. **"The reported symptom always points at the right layer."** As multiple scenarios above show, an accurate symptom report is frequently paired with an incorrect inference about which layer or component is responsible.
3. **"A fast answer is always a better answer."** A fast, unstructured guess that happens to be right reads as luck; a structured, slightly slower answer that names its evidence at each step reads as skill — interviewers generally weight the latter more heavily, especially at Senior/Architect tiers.
4. **"Once the immediate symptom is fixed, the scenario is fully answered."** The strongest answers explicitly address prevention/recurrence (fixing the automation, not just the certificate; tightening the rule, not just working around it once).

## 13. 🔑 Key Takeaways

- Every scenario in this section is built around one sharp discriminating clue in its phrasing — training yourself to spot that clue is the core skill this section drills, more so than memorizing the specific answers.
- A complete scenario answer names the hypothesis, the tool/evidence that would confirm it, and the specific remediation — stopping short of any of these three reads as less rigorous.
- The tools required across every scenario here are drawn entirely from Part 14 ([§115](../Part14/Section-115-Part14-A-Systematic-Troubleshooting-Methodology-OSI-Layer-Walkthrough.md)-[§123](../Part14/Section-123-Part14-Common-Failure-Scenarios-and-Root-Cause-Case-Studies.md)) — this section is deliberately about sequencing and interpretation, not new technique.
- The strongest answers explicitly separate "what happened" from "why it won't happen again," addressing both the immediate fix and the underlying prevention.
