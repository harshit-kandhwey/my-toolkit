# Section 142 (Part 17): System Design Questions Involving Networking (Load Balancers, CDNs, DNS)

## 1. Design Question Bank: Load Balancing and Traffic Distribution

**Design Q1.** Design the traffic-distribution layer for a public web application expecting a sudden 10x traffic spike during a scheduled product launch. What load-balancing choices do you make, and why?
**Model answer:** I'd use a managed cloud load balancer ([§80](../Part9/Section-80-Part9-Cloud-Load-Balancer-Types-ALB-NLB-Azure-LB-App-Gateway-GCP-LB-Conceptual.md)) rather than a self-managed NGINX/HAProxy/Envoy fleet ([§81](../Part9/Section-81-Part9-Software-Load-Balancers-NGINX-HAProxy-Envoy-Conceptual-Comparison.md)) specifically because the sudden, predictable spike benefits from the provider's own elastic capacity rather than needing to pre-provision and manage scaling of my own LB tier. I'd choose Layer 7 ([§73](../Part9/Section-73-Part9-Layer-4-vs-Layer-7-Load-Balancing.md)) so I can route by path (`/api` vs `/static`) and apply differentiated health checks ([§75](../Part9/Section-75-Part9-Health-Checks-and-Failover-Behavior.md)) per backend pool. For session-sensitive parts of the app, I'd evaluate whether sticky sessions ([§77](../Part9/Section-77-Part9-Session-Persistence-Sticky-Sessions-and-Its-Trade-Offs.md)) are actually needed — for a stateless API, avoiding sticky sessions entirely lets any healthy backend serve any request, maximizing the benefit of horizontal autoscaling during the spike. I'd pre-warm the load balancer with the cloud provider ahead of a known traffic event, since some managed LBs scale their own capacity gradually rather than instantaneously.

**Design Q2.** You operate services in three regions and want to route users to the nearest healthy region automatically, with automatic failover if a region goes down. Design this.
**Model answer:** This is a Global Server Load Balancing (GSLB) problem ([§79](../Part9/Section-79-Part9-Global-Server-Load-Balancing-GSLB-and-Anycast.md)) — I'd use DNS-based geographic routing (returning different regional IPs based on the resolver's location) combined with active health checking of each region's endpoint, so an unhealthy region is automatically removed from the DNS answer set. For latency-sensitive static content, I'd add Anycast ([§79](../Part9/Section-79-Part9-Global-Server-Load-Balancing-GSLB-and-Anycast.md)) at the CDN edge layer so the same IP is announced from multiple locations and BGP naturally routes each user to the topologically nearest one. I'd keep TTLs on the GSLB DNS records low enough (but not so low they cause excessive query load) that failover propagates within an acceptable window, and I'd test regional failover deliberately and regularly rather than only during a real incident.

**Design Q3.** Design the load-balancer and traffic architecture for a mixed environment: a legacy monolith on static VMs, and a fast-growing set of Kubernetes-hosted microservices, both needing to be reachable from the internet.
**Model answer:** I would not force one tool across both halves. For the monolith's static, infrequently-changing backend set, a traditional load balancer (managed cloud LB, or HAProxy/NGINX, [§81](../Part9/Section-81-Part9-Software-Load-Balancers-NGINX-HAProxy-Envoy-Conceptual-Comparison.md)) with its reload-on-change configuration model is entirely adequate — the operational cost of that model is near zero when backends rarely change. For the Kubernetes microservices, I'd rely on Envoy ([§81](../Part9/Section-81-Part9-Software-Load-Balancers-NGINX-HAProxy-Envoy-Conceptual-Comparison.md)) as the Ingress controller's engine, or a service mesh's sidecar data plane, specifically because its dynamic, API-driven configuration model matches the constantly-changing pod set that environment produces. At the boundary between the two worlds, I'd design an explicit, well-understood gateway (an API gateway pattern, [§78](../Part9/Section-78-Part9-Reverse-Proxies-vs-Load-Balancers-vs-API-Gateways.md)) rather than trying to unify the tooling underneath both halves, since each environment's actual change velocity is what should drive its own tool choice.

**Design Q4.** A backend service behind a load balancer intermittently returns 502 errors under moderate load, but individual backend instances respond correctly when tested directly. Diagnose the likely architectural gap and redesign to prevent it.
**Model answer:** This pattern usually indicates a mismatch between the load balancer's and the backend's idle-connection/keep-alive timeouts — the backend closes an idle connection the load balancer still considers reusable, and the next request over that stale connection gets a 502. I'd redesign by explicitly setting the backend's keep-alive timeout to be *longer* than the load balancer's idle timeout (never the reverse), and I'd verify health-check configuration ([§75](../Part9/Section-75-Part9-Health-Checks-and-Failover-Behavior.md)) isn't flapping backends in and out of the pool under load, which produces a similar symptom. I'd also add connection-level metrics (RST rates specifically) as a first-class dashboard signal, since a rising RST rate against backends is a leading indicator of exactly this class of problem before customer-facing error rates rise.

## 2. Design Question Bank: CDN, Caching, and Edge Architecture

**Design Q5.** Design a CDN strategy for a media-heavy site (images, video) with a global audience, balancing cost, latency, and cache-invalidation correctness.
**Model answer:** I'd push static, versioned assets (images, JS/CSS bundles with content-hashed filenames) to the CDN with long TTLs and effectively never need to invalidate them, since a new deploy simply produces new filenames — this sidesteps the cache-invalidation problem entirely for the highest-volume content. For content that must be invalidated (a CMS-edited page, a corrected image at a stable URL), I'd use short TTLs plus an explicit purge/invalidation API call triggered by the publishing workflow, rather than relying on TTL expiry alone to propagate corrections. I'd choose a CDN provider with strong Anycast-based edge presence in the audience's actual geographic distribution, and I'd monitor cache-hit ratio explicitly as a cost and performance signal — a low hit ratio on content expected to be highly cacheable points at a caching-header or invalidation-logic bug worth fixing before it's masked by simply adding more edge capacity.

**Design Q6.** Your API sits behind a CDN for DDoS protection and TLS termination, but a customer complains their specific IP-based rate-limiting integration broke after adopting the CDN. Explain why, and redesign.
**Model answer:** The CDN terminates the client's TCP/TLS connection at the edge and opens its own connection to the origin — from the origin's perspective, every request now appears to originate from the CDN's edge IP, not the real client's IP, breaking any origin-side logic that keyed on source IP directly. The fix is to have the CDN forward the real client IP in a header (commonly `X-Forwarded-For` or a provider-specific equivalent) and have the origin's rate-limiting logic read from that header instead of the raw connection's source IP — with the important caveat that the origin must only trust that header when the connection genuinely originates from the CDN's known IP ranges, since an attacker who could reach the origin directly could otherwise spoof the header to bypass rate limiting entirely.

**Design Q7.** Design DNS architecture for a service that must support blue/green deployments with instant, safe rollback capability at the DNS layer.
**Model answer:** I'd lower the record's TTL well ahead of the planned cutover (a standard practice — e.g., to 60 seconds, a day or more in advance) so that both the cutover and any rollback propagate quickly and predictably rather than being at the mercy of a long, previously-set TTL. I'd use a weighted or failover DNS routing policy (common in managed cloud DNS services) to shift traffic gradually from blue to green rather than an all-or-nothing cutover, watching error rates at each weight increment before proceeding further. If green shows problems, rolling back is simply shifting the weight back — because the TTL is already short and both blue and green environments remain warm and running during the transition, rollback is fast rather than requiring a fresh deploy. I'd raise the TTL back to its normal value only once green is confirmed stable and blue is safely decommissioned.

**Design Q11.** A gaming company runs a real-time multiplayer service using UDP for low-latency state updates. Design the load-balancing and traffic-distribution layer, explaining why a typical Layer 7 HTTP load balancer is the wrong tool.
**Model answer:** A Layer 7 load balancer's value (path-based routing, HTTP header inspection) is irrelevant to a raw UDP game-state protocol, and terminating/re-establishing connections at Layer 7 would add exactly the latency this workload can least afford. I'd use a Layer 4 load balancer ([§73](../Part9/Section-73-Part9-Layer-4-vs-Layer-7-Load-Balancing.md)) that forwards UDP datagrams by IP/port without inspecting or re-terminating them, or in some designs, rely on client-side connection persistence to a specific game-server instance (assigned once at session start, since mid-session load-balancer re-routing for a stateful, low-latency UDP session is far more disruptive than for a stateless HTTP request) rather than round-robining every packet. I'd pick the load-balancing algorithm ([§74](../Part9/Section-74-Part9-Load-Balancing-Algorithms-Round-Robin-Least-Connections-Weighted-Hashing.md)) based on active player-session count per server rather than raw connection count, since a "least connections" metric doesn't map well to a protocol that isn't really "connections" in the TCP sense.

## 5. Design Question Bank: DNS-Centric and Hybrid System Design

**Design Q8.** Design a service-discovery mechanism for a microservices platform spanning both a Kubernetes cluster and a set of legacy VMs outside the cluster, where services on both sides need to discover and call each other by name.
**Model answer:** Inside Kubernetes, I'd rely on the built-in cluster DNS and Service abstraction ([§111](../Part13/Section-111-Part13-The-Kubernetes-Networking-Model-Pod-to-Pod-Service-and-Ingress-Concepts.md)) for pod-to-pod and pod-to-Service discovery — that's the native, already-solved mechanism and reinventing it would add needless complexity. For legacy VMs needing to reach Kubernetes-hosted services, I'd expose those services through a stable Ingress or load-balancer-backed DNS name in the organization's regular DNS zone, rather than trying to expose internal cluster DNS directly to the VM network. For the reverse direction (Kubernetes services calling legacy VM services), I'd register the VMs in the same external/internal DNS zone with stable names, and could optionally use a private cloud-DNS zone ([§107](../Part12/Section-107-Part12-Cloud-DNS-and-Service-Discovery-Patterns.md)) as the shared source of truth both sides resolve against. I'd explicitly avoid split-brain naming — one shared, authoritative internal DNS zone that both the cluster's external-facing names and the legacy VMs' names live in, rather than two independently-maintained naming schemes that could drift out of sync.

**Design Q9.** A company wants a single global API domain (`api.example.com`) that transparently routes each request to the nearest of five regional deployments, fails over automatically if a region is unhealthy, and never serves a customer from a region that has fallen out of a compliance-mandated data residency boundary. Design this.
**Model answer:** I'd combine GSLB-style latency/geo-based DNS routing ([§79](../Part9/Section-79-Part9-Global-Server-Load-Balancing-GSLB-and-Anycast.md)) as the base mechanism, with health-check-driven automatic removal of unhealthy regions from the answer set. For the compliance constraint, I would not rely on DNS geo-routing alone (a resolver's apparent location doesn't perfectly guarantee the requesting client's true jurisdiction) — I'd add an explicit, deliberate residency-aware routing policy at the DNS or edge layer that excludes non-compliant regions from ever being offered as an answer for clients whose jurisdiction requires it, verified independently at the application layer as a second check rather than trusting network-layer routing alone for a compliance-critical guarantee. I'd keep TTLs low enough for fast regional failover while monitoring query volume, since compliance and failover pull TTL sizing in the same direction (both want fast propagation) but cost pulls the other way (more queries at very low TTLs) — a genuine, explicit trade-off to size deliberately rather than default blindly.

**Design Q10.** Design the load-balancing and DNS architecture for an internal-only platform API used exclusively by other internal services within the same VPC, with no public internet exposure at any point.
**Model answer:** I would not reach for a public-facing CDN or public DNS at all — this is purely an internal-traffic problem. I'd use an internal (private) load balancer, not internet-facing, so the load balancer itself has no public IP and can't be discovered or reached from outside the VPC. For naming, I'd use the cloud provider's private/internal DNS zone ([§107](../Part12/Section-107-Part12-Cloud-DNS-and-Service-Discovery-Patterns.md)) rather than public DNS, so the service's name never resolves outside the private network at all — this is a stronger boundary than relying on firewall/security-group rules alone to keep an otherwise publicly-resolvable name unreachable. I'd apply the same health-check and load-balancing algorithm choices ([§74](../Part9/Section-74-Part9-Load-Balancing-Algorithms-Round-Robin-Least-Connections-Weighted-Hashing.md)-[§75](../Part9/Section-75-Part9-Health-Checks-and-Failover-Behavior.md)) as a public-facing service, since internal traffic still benefits from load distribution and failure detection — internal-only doesn't mean lower operational rigor, just a smaller, more trusted network boundary.

**Design Q12.** Design a DNS-based canary release strategy for shifting 5% of traffic to a new API version, with the ability to abort within minutes if error rates spike.
**Model answer:** I'd lower the relevant record's TTL well ahead of the canary window (matching the blue/green pattern in Design Q7), then use a weighted DNS routing policy sending roughly 5% of resolutions to the new version's endpoint and 95% to the stable version. I'd instrument both versions identically and watch error rate and latency specifically for the canary's traffic slice, not just an aggregate — because DNS weighting is probabilistic per-resolution rather than per-request, some resolvers/clients will cache their assigned version for the TTL duration, so "abort within minutes" requires the short TTL to actually propagate that fast, and I'd explicitly test this propagation time before relying on it during a real incident, since DNS-based canarying is inherently coarser and slower than an application-layer (Layer 7 load balancer, weighted routing at the LB itself) canary mechanism — for genuinely fast abort requirements, I'd prefer Layer 7 weighted routing over DNS weighting specifically because it doesn't depend on client-side cache expiry at all.

## 6. Production Usage Notes

- Real system-design interviews rarely have one "correct" answer — interviewers are evaluating whether the trade-offs named are genuine and specific to the stated constraints, not whether the candidate arrives at the exact architecture the interviewer had in mind.
- A candidate who proactively names a design's weakest point (Design Q4's timeout mismatch, Design Q9's compliance edge case) before being asked reads as substantially more senior than one who only defends the design when challenged.
- Drawing the architecture (even roughly, in a shared doc or whiteboard) while talking through it is a real, expected part of most system-design interviews — practicing verbal-only explanation is necessary but not sufficient preparation.

## 7. Security Considerations

- Design Q6's `X-Forwarded-For` trust boundary is a genuinely common real-world vulnerability class — any design that trusts a client-supplied or intermediary-supplied header for a security-relevant decision (rate limiting, IP allowlisting) must also explicitly restrict which upstream sources are trusted to set that header at all.
- Design Q9's compliance/data-residency scenario illustrates that network-layer routing (DNS geo-routing) is a heuristic, not a compliance guarantee — any system-design answer touching legal/compliance boundaries should explicitly flag where an additional, non-network-layer control is required rather than presenting DNS-based routing alone as sufficient.
- Design Q10's internal-only architecture demonstrates defense-in-depth thinking: relying on "not publicly resolvable" (private DNS) as one layer, and firewall/security-group restriction as another, independent layer — never collapsing a system design down to a single control for a security-relevant boundary.

## 8. Common Troubleshooting Scenarios

| Symptom in a System-Design Follow-Up                                | Likely Design Gap                                                             | Redesign Direction                                                                                              |
| ------------------------------------------------------------------------ | -------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| "What happens if your load balancer's health check has a false positive?" | No distinction made between transient and sustained failure in health-check logic | Add configurable failure thresholds/hysteresis ([§75](../Part9/Section-75-Part9-Health-Checks-and-Failover-Behavior.md)) before marking a backend unhealthy, not a single-check trigger |
| "What if the CDN itself has an outage?"                                  | Single point of failure at the CDN/edge layer with no origin fallback path       | Design an explicit, tested origin-fallback or multi-CDN failover path, not an assumption that the CDN never fails |
| "How does your DNS failover interact with client-side DNS caching outside your control?" | Design assumed TTL is respected everywhere, ignoring resolvers/clients that cache longer than instructed | Acknowledge the limitation explicitly and design for graceful degradation (health-check-aware backend behavior) rather than relying purely on DNS propagation speed |
| "What's the blast radius if your rate-limiting header trust boundary is misconfigured?" | Missing explicit restriction on which upstream sources are trusted to set forwarded-IP headers | Add and test an explicit allowlist of trusted intermediary IP ranges before accepting a forwarded-IP header value |

## 9. Best Practices

- Always state the actual constraint being optimized for (cost, latency, correctness-under-failure, compliance) before naming components — a design that's excellent for one constraint can be poor for another, and naming the constraint first shows deliberate reasoning rather than a memorized reference architecture.
- Explicitly name at least one trade-off and one failure mode for every non-trivial design choice, unprompted — this is consistently one of the highest-signal behaviors interviewers look for at Senior/Architect tiers.
- When a design spans multiple previously-covered concepts (load balancing + DNS + TLS termination, as in most questions here), explicitly connect them rather than describing each component in isolation — the actual skill being tested is composition, not component recall.
- Practice sketching these designs on a literal whiteboard or shared doc, not just narrating them, since that's the real format most system-design interviews use.

## 10. Common Anti-Patterns / Mistakes

- **Defaulting to the most modern or most-discussed component (service mesh, multi-region active-active, a specific cloud-native product) without justifying why it fits the stated constraint.** A simpler design that correctly fits the actual requirement is a stronger answer than an impressive-sounding one that doesn't.
- **Describing a design without ever naming a trade-off or failure mode.** Interviewers specifically probe for this omission with a follow-up question; naming it proactively is stronger than only producing it under prompting.
- **Treating DNS-based routing (GSLB, geo-routing) as an absolute, instantaneous guarantee.** DNS propagation is TTL-bound and resolver-cache-dependent — any design relying on it for failover or compliance boundaries should explicitly acknowledge this limitation.
- **Designing the happy path only and leaving the failure/rollback path implicit.** Design Q7's blue/green scenario specifically rewards a candidate who designs the rollback path with the same rigor as the forward cutover path.

## 11. Interview Questions

**🎯 Beginner:** _"What's the difference between a load balancer and a CDN, and could you use both together?"_
**Model answer:** A load balancer distributes traffic across a pool of backend servers, typically within one region or data center, to improve availability and scale. A CDN caches and serves content from geographically distributed edge locations, closest to each user, primarily to reduce latency and offload traffic from the origin. They solve different problems and are commonly used together: a CDN sits in front of a load balancer, serving cacheable content directly from the edge and forwarding only cache-miss or dynamic requests back to the load balancer and origin servers.
_What the interviewer is probing for:_ Basic conceptual clarity on two commonly conflated components.

**🎯 Intermediate:** _"Design the DNS and load-balancing setup for a service that needs to survive an entire region going offline without manual intervention."_
**Model answer:** I'd deploy the service in at least two regions behind a GSLB-style DNS configuration with active health checks on each region's endpoint — a region failing its health check is automatically removed from the DNS answer set, redirecting new connections to the remaining healthy region(s) without a human needing to intervene. I'd keep the DNS TTL low enough that this failover propagates within an acceptable window, and I'd regularly test the failover path deliberately (not just assume it works because it was configured once), since untested failover mechanisms are a common source of surprise failures during a real regional outage.
_What the interviewer is probing for:_ Whether the candidate can design genuine automatic failover, not just multi-region deployment without an automated failover mechanism.

**🎯 Senior:** _"Your load-balanced service occasionally serves a stale response from one backend right after a deploy, even though the deploy process marks each instance healthy before routing traffic to it. Diagnose and redesign."_
**Model answer:** "Marked healthy" after a deploy is often based on a shallow health check (process is up, port is listening) rather than confirming the new version is actually fully warmed up and serving correct responses — a backend can pass a shallow check while still initializing caches, connection pools, or lazy-loaded data, causing early requests to it to be served incorrectly or slowly. I'd redesign the health check to be deeper and version-aware (confirming a specific expected response or version marker, not just a 200 status), and I'd add a brief, deliberate warm-up period after health-check-pass before sending full production traffic weight to a newly deployed instance, ramping traffic gradually rather than switching all-at-once.
_What the interviewer is probing for:_ Recognition that health-check depth and deploy-time traffic ramping are real, distinct design levers, not just "add a health check" as a generic answer.

**🎯 Architect:** _"Design the end-to-end request path — from a mobile client to a database write — for a global e-commerce platform, explicitly identifying every point where networking design decisions materially affect availability, latency, or security."_
**Model answer:** Starting from the client: DNS resolution to the nearest region via GSLB ([§79](../Part9/Section-79-Part9-Global-Server-Load-Balancing-GSLB-and-Anycast.md)), TLS termination at a CDN/edge layer ([§65](../Part8/Section-65-Part8-TLS-SSL-Fundamentals-Handshake-Certificates-Cipher-Suites.md)-[§66](../Part8/Section-66-Part8-Certificate-Authorities-Chains-of-Trust-and-Lets-Encrypt-ACME.md)) for latency and centralized certificate management, with the CDN forwarding real client IP for downstream rate-limiting and fraud-detection logic (with an explicit trust boundary on that forwarded header). Edge-to-origin traffic re-encrypted with TLS rather than passed in plaintext internally, consistent with a zero-trust posture ([§86](../Part10/Section-86-Part10-Network-Segmentation-and-Zero-Trust-Networking-Principles.md)). At the origin, a Layer 7 load balancer ([§73](../Part9/Section-73-Part9-Layer-4-vs-Layer-7-Load-Balancing.md)) routes by path to the appropriate microservice, each service instance passing deep, version-aware health checks ([§75](../Part9/Section-75-Part9-Health-Checks-and-Failover-Behavior.md)) before receiving traffic. Service-to-service calls within the cluster use the platform's internal service discovery and mesh sidecar proxies ([§113](../Part13/Section-113-Part13-Service-Mesh-Networking-Concepts-Sidecar-Proxies-mTLS.md)) for mTLS and dynamic routing. The final database write travels through a private, non-internet-routable subnet ([§100](../Part12/Section-100-Part12-Cloud-Virtual-Networking-Fundamentals-VPC-VNet-Concepts-Across-Providers.md)-[§104](../Part12/Section-104-Part12-Hub-and-Spoke-and-Transit-Gateway-Hub-Architectures.md)) with security-group rules scoped to only the specific application tier's source range, and NAT/PAT ([§20](../Part3/Section-20-Part3-NAT-and-PAT-Concepts-and-Real-World-Use.md)) handles any legitimate outbound-only traffic from that tier without exposing it to unsolicited inbound connections. At every boundary named above, I'd flag the specific availability risk (a single-region DNS failure point, an under-provisioned NAT gateway under connection churn), the specific latency cost (each additional TLS termination/re-encryption hop), and the specific security control (mTLS internally, narrow security-group scoping at the data tier) — a mature system design names all three explicitly at every hop, not just at the edges of the request path.
_What the interviewer is probing for:_ Whether the candidate can hold and correctly sequence the entire cross-cutting request path from client to data tier, citing the specific mechanism at each hop rather than a vague high-level sketch — this is the capstone-level synthesis question this entire knowledge base has been building toward.

## 12. Common Misconceptions

1. **"A system-design interview is testing whether you know the 'right' architecture."** It is testing whether the trade-offs you name for your chosen architecture are genuine, specific, and correctly reasoned — there is rarely one uniquely correct answer.
2. **"More components (CDN + multi-region + service mesh + everything) is always a stronger design."** An over-engineered design that doesn't map its complexity to an actual stated requirement reads as weaker than a simpler, well-justified one.
3. **"DNS-based failover is instantaneous."** It is bound by TTL and by resolvers/clients that may cache longer than intended — a strong design acknowledges this propagation delay explicitly rather than treating DNS failover as instant.
4. **"Naming a security or compliance concern is optional unless the interviewer asks about security specifically."** As shown in Design Q6 and Q9, security- and compliance-relevant trade-offs are woven into ordinary system-design questions, and proactively naming them is a consistently rewarded senior signal.

## 13. 🔑 Key Takeaways

- A strong system-design answer follows a five-step shape: restate the real constraint, choose components with explicit justification, name the trade-off, identify the design's weakest point, and state what would be monitored to confirm it's working.
- DNS-based routing and failover mechanisms (GSLB, geo-routing, blue/green cutovers) are all fundamentally TTL- and cache-bound — every design relying on them should explicitly acknowledge that propagation is not instantaneous.
- CDN/load-balancer architectures that terminate and re-establish connections change what the origin can see (source IP, TLS details) — any design relying on that information downstream must account for this and establish an explicit trust boundary for forwarded headers.
- The strongest, most senior-reading answers proactively name a design's failure mode and its security/compliance implications without being separately prompted for either.
