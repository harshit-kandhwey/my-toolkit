# Section 111 (Part 15): Linux Administration Best Practices Checklist

## 1. Why a Checklist, and Why It Needs Reasoning Attached

Part 14 closed with §110's compliance and governance coverage — the organizational layer that determines whether technical controls are actually followed in practice, not just documented. That section is the natural bridge into this one: Part 15 as a whole is a **synthesis and mastery Part**, not a source of new topics. Every item below was already introduced somewhere in Parts 1–14; what this section adds is organization — pulling scattered, individually-justified practices into one categorized reference — and, critically, **reasoning attached to each item**.

A checklist without reasoning teaches rule-following: "always do X" memorized without understanding why X matters degrades the moment a situation doesn't quite match the rule as memorized, and the administrator has nothing to fall back on. A checklist with reasoning teaches judgment: understanding _why_ least-privilege sudo scoping matters means recognizing the same underlying principle in a situation the checklist never explicitly listed — a new tool, a new cloud service, a scenario nobody wrote a rule for yet. That's the actual goal of this section, and of Part 15 generally: consolidating five categories worth of accumulated judgment rather than introducing a sixth new topic.

> 💡 **Tip:** When reviewing this checklist against a real environment, don't just check items off — for each one, ask "do I know why this matters, specifically, for the systems I run?" If the answer is no, that's a gap in judgment even if the box can technically be checked. A checklist item satisfied by accident, without understanding why, is one incident away from being un-satisfied the next time circumstances change slightly.

## 2. Security

- **Least privilege via scoped sudo, not blanket root access (§31).** Granting a user unrestricted `sudo` (or worse, direct root login) when they only ever need to restart one service means every mistake, compromised credential, or malicious action by that account has the full blast radius of root, rather than the blast radius of the one narrow capability actually required. Scoping `/etc/sudoers` entries to specific commands (or specific command patterns via `Cmnd_Alias`) is more setup effort up front, but bounds the damage a single compromised account can do to exactly what that account was ever supposed to be able to do.
- **SSH key-based authentication, not passwords (§56, §90).** Password authentication over SSH is vulnerable to brute-force and credential-stuffing in a way key-based auth structurally isn't — an attacker needs the private key material itself, not just a guessable or leaked string. Disabling `PasswordAuthentication` in `sshd_config` closes an entire attack class rather than just making it statistically slower to succeed.
- **Keep systems patched on a defined cadence (§94).** Unpatched systems accumulate known, publicly-documented vulnerabilities over time — vulnerability management isn't a one-time hardening pass performed at provisioning time, it's an ongoing process because new CVEs are disclosed continuously against software that was fine yesterday and is a documented risk today.
- **Enforce Mandatory Access Control — SELinux or AppArmor — rather than relying on discretionary permissions alone (§91).** Standard Unix permissions (owner/group/other) are necessary but not sufficient — a compromised process running as a legitimate user can still do anything that user's discretionary permissions allow. MAC adds a second, independent layer that constrains what a process can do regardless of the invoking user's own permissions, which matters specifically when the process itself, rather than the user's own credentials, is what gets compromised (a web server exploited through a code vulnerability, for instance).
- **Manage secrets deliberately, never as plaintext config values (§92's secrets-management coverage).** Credentials embedded directly in scripts, configuration files, or left sitting in shell history are a routine, repeated source of accidental exposure — via an accidental git commit, verbose log output, or simple file readability by more accounts than intended — that a dedicated secrets-management approach avoids by design rather than by discipline alone.
- **Treat SSH hardening as a bastion-host-first concern (§90).** Exposing SSH directly on every host rather than funneling access through a hardened bastion multiplies the attack surface by the size of the fleet; a single, heavily monitored entry point is easier to secure thoroughly than dozens of individually-hardened endpoints.

## 3. Reliability

- **Backups that are actually tested, not just scheduled (§79, §106).** A backup job running successfully on a cron schedule proves data was written somewhere — it proves nothing about whether that data can actually be restored. §106's core point bears repeating here because it's this frequently violated in practice: an untested backup is not a backup, it's an unverified assumption, and the only way to know a restore procedure genuinely works is to have actually run it, ideally on a defined recurring schedule rather than once at setup time.
- **Monitoring and alerting configured before incidents happen, not built reactively after one (§80–§88).** Instrumenting CPU, memory, disk, and network as a unified model (§80) and setting alert thresholds ahead of time means an emerging problem is caught while it's still cheap to fix — waiting until a user-facing outage forces attention means the same signal was available all along but nobody was watching for it, which is a strictly worse outcome for identical underlying data.
- **Documented runbooks for known failure modes (§87).** A structured troubleshooting methodology applied for the first time, live, during an actual incident is slower and more error-prone than the same methodology applied from a runbook written calmly beforehand — the value of a runbook isn't the information itself, it's having that information reliably available under time pressure, when working memory is at its least reliable and the cost of a wrong guess is highest.
- **Design for the actual failure modes the fleet will encounter (§105, §106) rather than assuming hardware and networks don't fail.** High-availability architecture and disaster-recovery planning are cheap relative to the cost of discovering, mid-incident, that no such plan existed — the investment is asymmetric, and that asymmetry only becomes obvious in hindsight, after the outage that could have been avoided.
- **Capacity-plan proactively rather than scaling reactively under load (§107).** Understanding a fleet's growth trajectory and provisioning ahead of demand avoids the specific failure mode where infrastructure runs out of headroom exactly when demand is highest and least tolerant of degraded performance.

## 4. Operational Hygiene

- **Configuration management over manually-configured snowflake servers (§97, §98).** A host configured by hand, one SSH session and one ad hoc change at a time, drifts from every other host in the fleet and eventually becomes a system nobody fully understands or can safely reproduce. Configuration management tools enforce **idempotency and desired state** — the same declared configuration applied twice produces the same result, and that declared configuration is itself the documentation of what the host should look like, rather than documentation being a separate artifact that inevitably goes stale.
- **Version-controlled infrastructure definitions (§97).** Infrastructure-as-code checked into version control gives every change a reviewable diff, an author, a timestamp, and a rollback path — the same discipline already applied to application code for decades, extended to the infrastructure that runs it, closing a gap that used to exist between how carefully application changes and infrastructure changes were tracked.
- **Consistent naming and tagging conventions across the fleet.** A host or resource named or tagged inconsistently is a host that's harder to find, harder to attribute cost to (§109's cost-optimization tagging point), harder to include correctly in automation that matches on naming patterns, and harder to safely decommission with confidence that nothing else depends on it. At fleet scale, naming discipline is what makes automation and cost accounting tractable at all.
- **Golden images and immutable infrastructure where practical (§102).** Rebuilding from a known-good image rather than patching a long-lived host in place avoids the accumulation of undocumented, one-off changes that produces snowflake servers in the first place — the fleet's actual state stays traceable to a specific, known image build rather than an unrecorded history of individual patches.
- **CI/CD runners and pipelines treated with the same hygiene as production hosts (§100).** A build/deploy pipeline that's itself a snowflake, manually patched and undocumented, is a single point of failure for every deployment that depends on it — the same configuration-management discipline that applies to application hosts applies equally to the infrastructure that ships changes to them.

## 5. Change Management

- **Test changes before they reach production (§108).** Blue/green and canary deployment patterns exist specifically because "it worked when I tried it locally" and "it will work identically under production load, on production data, at production scale" are different claims — validating a change against a smaller blast radius before full rollout catches the gap between those two claims while it's still cheap to correct.
- **Have a rollback plan decided before deploying, not improvised after something breaks.** A rollback path designed under calm, pre-deployment conditions is more reliable than one improvised mid-incident, under pressure, with a production system actively degraded — the same underlying reasoning as runbooks in 3: decisions made ahead of time under low stress are better decisions than the same decisions made under time pressure with an active outage in progress.
- **Route changes through approval and evidence-retention processes appropriate to the environment (§110).** Even outside a formally regulated environment, a lightweight change-review step catches mistakes a single engineer working alone is structurally prone to miss — a second reviewer isn't redundant, it's a different set of assumptions checking the first, and the value doesn't require a compliance mandate to be real.
- **Prefer in-place patching vs. reimage decisions made deliberately, not by default (§108).** Whether a given upgrade should be an in-place patch or a full host reimage is itself a decision with trade-offs — an organization that always defaults to one approach without considering the other is optimizing for habit rather than for the specific change's actual risk profile.

## 6. Documentation

- **Runbooks, architecture decisions, and operational context written down, not held only in one person's memory (§87).** The practical risk here is concrete, not abstract: undocumented tribal knowledge is a real operational liability the day the one person who understood it leaves, goes on leave, or is simply unavailable during an incident at three in the morning. Documentation isn't overhead layered on top of the real work — it's what lets the operational knowledge survive any single individual's absence.
- **Document the "why" behind non-obvious configuration, not just the "what."** A configuration value with no recorded rationale looks safe to "clean up" or change later by someone who doesn't know why it was set that way — the reasoning is what prevents a well-intentioned future change from reintroducing a problem the original setting was specifically there to avoid.
- **Keep documentation close to what it describes, and updated as part of the change itself.** Documentation maintained as a separate, occasional exercise drifts from reality quickly; documentation updated as a required part of the same change that alters the underlying system stays accurate because it's treated as part of the deliverable, not an afterthought.

## 8. Worked Scenario: Applying the Checklist to a Real Handoff

Consider a concrete situation that pulls every category together at once: an administrator inherits a 40-host fleet from a departing colleague, with no handoff documentation beyond a spreadsheet of hostnames.

- **Security first.** Before anything else, audit who has access — check `/etc/sudoers` on each host for overly broad grants (2), confirm `PasswordAuthentication` is actually disabled in `sshd_config` rather than assumed (2), and check patch levels against the organization's defined cadence (2) rather than trusting that "someone was probably keeping this current."
- **Reliability next.** Locate the backup jobs, and treat their existence with suspicion until a restore has actually been attempted (3) — a scheduled job with a green history proves nothing about restorability. Check whether any monitoring/alerting exists at all, and if it does, whether the alert thresholds still make sense for current load (3).
- **Operational hygiene.** Determine whether any of the 40 hosts are under configuration management or whether they're all snowflakes accumulated over years (4) — this shapes the entire remediation plan, since bringing an unmanaged fleet under management is itself a significant, incremental project (9's architect-level answer covers this directly).
- **Change management.** Until the fleet's actual state is understood, avoid making changes that lack an explicit rollback path (5) — the temptation to "clean things up immediately" is real, but doing so before understanding what's actually running risks breaking dependencies nobody has documented yet.
- **Documentation.** Everything discovered during this audit should be written down as it's found, not after the fact from memory (6) — this audit is itself the first real documentation this fleet may have ever had, and capturing it in the moment prevents the next handoff from starting at the same deficit.

The point of walking through this scenario explicitly: the five categories aren't independent silos to satisfy one at a time — a real operational situation like an undocumented handoff touches all five simultaneously, and the checklist's value is in giving the incoming administrator a structured order of operations rather than an overwhelming, undifferentiated pile of concerns.

## 9. Common Misconceptions

1. **"A best-practices checklist is a substitute for understanding the systems it applies to."** The checklist is a memory aid and an organizing structure for judgment already built through understanding — it isn't a replacement for that understanding, and applying it mechanically without the reasoning behind each item is exactly the failure mode 1 warns against.
2. **"These practices only matter at large enterprise scale."** Several — tested backups, SSH key-only auth, documented runbooks — matter identically on a single-host personal project and a thousand-host fleet; what changes with scale is the cost of skipping them, not whether they apply at all.
3. **"Following every item on this list means the environment is fully secure and reliable."** This checklist synthesizes established practice, but §110 already established that even full compliance with a much narrower CIS-style checklist is a floor, not a ceiling — the same caution applies here.

## 10. Tiered Interview Questions

**🎯 Beginner:** _"Why is it considered bad practice to always log in as root or run every service as root?"_
**Model answer:** Running as root removes any boundary between what an account can normally do and what it can do if something goes wrong — a mistake, a bug, or a compromise in a process running as root has the full run of the system, whereas the same failure in a process running under a scoped, unprivileged account is contained to whatever narrow permissions that account has. Least-privilege scoping (§31) means every account and process only has the access it actually needs, so the blast radius of any single failure is bounded rather than total.
_What the interviewer is probing for:_ Whether the candidate understands least privilege as a blast-radius argument, not just "root is dangerous" as an unexplained rule.

**🎯 Intermediate:** _"You inherit a fleet where backups run nightly and have never failed a job. Is that sufficient evidence the backups are reliable?"_
**Model answer:** No — a successful backup job proves data was written somewhere, not that it can be restored. Corruption, incomplete captures, or a restore procedure that was never actually exercised can all sit invisibly behind a green checkmark indefinitely. The only real evidence of reliability is a periodically tested restore (§106) — scheduling actual restore drills, not just monitoring job exit codes, and treating "can we restore from this today" as the metric that matters.
_What the interviewer is probing for:_ Recognition that job success and restorability are different claims, and that untested backups are a common, real operational trap rather than a purely theoretical one.

**🎯 Senior:** _"How would you decide what belongs in a runbook versus what should just be left to an engineer's judgment during an incident?"_
**Model answer:** Runbooks should capture the parts of incident response that are well-understood, recurring, and don't benefit from being reinvented under pressure — known failure modes with known diagnostic steps and known remediations (disk full, a specific service crash-looping, a known saturation pattern). Judgment stays valuable for genuinely novel situations a runbook can't anticipate. The reasoning is that working memory and decision quality both degrade under incident pressure (§87), so anything that can be pre-decided and documented should be, freeing actual judgment for the parts of the incident that are actually novel rather than re-deriving a known procedure from scratch under stress.
_What the interviewer is probing for:_ Understanding runbooks as a tool for preserving decision quality under pressure, not a rigid substitute for expertise, and the ability to distinguish "known and documentable" from "genuinely requires judgment in the moment."

**🎯 Architect:** _"An organization asks you to roll out configuration management across a fleet that's been managed manually for years. What's your approach, and what risks do you anticipate?"_
**Model answer:** I'd start by auditing the fleet's actual current state rather than assuming it matches any existing documentation — manually managed fleets accumulate snowflake drift (§98, and directly the subject of §112's anti-pattern coverage), so the first real work is discovering what's actually running, not assuming the intended configuration matches reality. I'd bring hosts under management incrementally, in small batches, verifying each batch converges to the declared state without unexpected side effects before proceeding, rather than converting the entire fleet at once and discovering an unanticipated divergence across hundreds of hosts simultaneously. I'd expect to find configuration or behavior that exists for reasons nobody currently at the organization remembers — the "why" documentation gap this section's Documentation category calls out directly — and I'd treat unexplained configuration as something to investigate and preserve deliberately rather than something safe to normalize away just because it doesn't fit the new declared state cleanly. Throughout, I'd track this as a change-managed initiative in its own right (§108-style testing and rollback planning), not an operational side project, since converting a fleet's management model is itself a significant production change.
_What the interviewer is probing for:_ Fleet-scale judgment — auditing before assuming, incremental rather than big-bang migration, respecting unexplained legacy behavior rather than dismissing it, and treating the migration itself with the same change-management discipline this checklist calls for elsewhere.

## 11. Key Takeaways

- This checklist deliberately organizes practices already established across Parts 1–14 by category (Security, Reliability, Operational Hygiene, Change Management, Documentation) rather than introducing new material — that's the nature of a Part 15 synthesis section.
- Every item carries a "why," because a checklist followed without understanding the underlying reasoning produces rule-following, not judgment — and judgment is what transfers to situations the checklist didn't explicitly anticipate.
- Several items reinforce each other across categories: tested backups (Reliability) depend on the same discipline as tested changes (Change Management); documented runbooks (Documentation) are what makes monitoring/alerting (Reliability) actionable during an actual incident rather than just noise.
- These practices apply at any scale — what changes with fleet size is the cost of skipping them, not their relevance.
- Full adherence to this checklist is still a floor, echoing §110's compliance-vs-security distinction — it establishes sound baseline judgment, not a guarantee against every possible failure.
