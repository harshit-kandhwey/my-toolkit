# Section 15 (Part 2): Interrupts, Context Switching, and CPU Scheduling Fundamentals

## 3. Interrupts: Hardware and Software

**Definition:** An interrupt is a signal that forces the CPU to suspend whatever it is currently executing and jump immediately to a fixed handler routine — the same "trap into the kernel" shape `[§11](./Section-11-Part2-System-Calls-Kernel-Userland-Boundary.md)` described for syscalls, but triggered by something other than the running program's own request.

There are two broad categories:

- **Hardware interrupts** — generated by a physical device to say "I need attention now": a NIC signaling a packet has arrived, a keyboard signaling a keypress, a disk controller signaling an I/O operation has completed. These arrive asynchronously, with no relationship to what the CPU happens to be running at that instant.
- **Software interrupts / traps** — generated deliberately by code currently executing on the CPU. The syscall mechanism from `[§11](./Section-11-Part2-System-Calls-Kernel-Userland-Boundary.md)` (the `syscall`/`svc` trap instruction) _is_ a software interrupt: a userspace program voluntarily triggers the same suspend-and-jump behavior a hardware device triggers involuntarily. Other software traps include CPU exceptions like a divide-by-zero or a page fault (`[§16](./Section-16-Part2-Virtual-Memory-Paging-Swap.md)`).

**The dispatch mechanism:** On x86, the CPU consults a kernel-maintained table — the **Interrupt Descriptor Table (IDT)** — indexed by interrupt/vector number, to find the address of the correct handler routine, called an **Interrupt Service Routine (ISR)**. A hardware interrupt controller (historically the PIC, on modern systems the **APIC** family) routes each device's signal to a specific vector number and can also route interrupts to specific CPU cores, which matters directly for the interrupt-storm scenario in 7. The dispatch sequence:

```text
Device (or CPU itself) raises an interrupt
        │
        ▼
Interrupt controller (APIC) delivers it to a CPU core, at a specific vector
        │
        ▼
CPU suspends current instruction stream, saves minimal state, consults the IDT
        │
        ▼
CPU jumps to the registered ISR for that vector number
        │
        ▼
ISR runs in kernel context, handles the interrupt (4 covers how "handles" is split)
        │
        ▼
CPU restores prior state and resumes — or, the scheduler decides a different task should run next (6)
```

⚠️ **Warning:** IDT layout, exact vector numbering, and APIC vs. legacy PIC behavior are architecture- and platform-specific implementation detail. Understand the shape — device signals CPU, CPU consults a table, jumps to a handler — rather than memorizing vector numbers; verify specifics against current architecture documentation if needed.

## 4. Top Half / Bottom Half: Why Interrupt Handlers Must Be Fast

An ISR runs with interrupts disabled (or at reduced priority) on the core handling it — while it runs, that core cannot promptly service other interrupts, and scheduling on that core is effectively frozen. A slow ISR therefore has an outsized, disproportionate cost: it doesn't just delay handling _its own_ device, it delays everything else waiting on that core, including the scheduler's ability to switch to a different runnable task.

The kernel's answer is to split interrupt handling into two halves:

- **Top half** — the actual ISR, runs immediately, does the absolute minimum urgent work (e.g., acknowledge the device, copy a small amount of data out of a hardware buffer before it's overwritten) and nothing more.
- **Bottom half** — the rest of the work, deferred to run later, with interrupts re-enabled, in a context where it's safe to take longer. Linux implements this deferral through **softirqs** (a fixed set of high-priority, statically-defined deferred handlers — network packet processing is a classic softirq user), **tasklets** (built on softirqs, used by individual drivers), and **workqueues** (deferred work that runs in genuine kernel _process_ context and, unlike softirqs/tasklets, is allowed to sleep).

```text
Interrupt arrives
        │
        ▼
TOP HALF (ISR)  — runs now, interrupts often disabled, must be fast:
  acknowledge device, stash minimal data, schedule bottom half
        │
        ▼
BOTTOM HALF (softirq / tasklet / workqueue) — runs shortly after,
  interrupts re-enabled, does the real work: full packet processing,
  filesystem completion handling, etc.
```

This split is genuinely important production knowledge: a driver or device that does too much work in its top half is a direct, measurable cause of system-wide latency spikes, because it is starving every other interrupt and scheduling decision on that core for the duration.

## 5. Context Switching

**Definition:** A context switch is the kernel operation that changes which process or thread is actually running on a CPU core — saving the complete register state of the task being suspended, and loading the previously-saved register state of the task about to run.

**What actually happens:**

1. The kernel saves the outgoing task's CPU register state (program counter, stack pointer, general-purpose registers, flags) into that task's kernel data structure (`task_struct` on Linux).
2. The kernel loads the incoming task's previously-saved register state into the CPU.
3. If the switch crosses process boundaries (not just switching between threads of the _same_ process), the kernel also switches the **virtual memory mapping** — reloading the page-table base register (CR3 on x86) so the CPU translates virtual addresses against the new process's address space (`[§16](./Section-16-Part2-Virtual-Memory-Paging-Swap.md)` covers page tables in depth).
4. Execution resumes at exactly the instruction the incoming task was suspended at.

**The real cost is not the register save/restore itself** — that part is a small, fixed, fast operation. The dominant cost is indirect: **cache invalidation**. The CPU's L1/L2 caches and the TLB (translation lookaside buffer, a cache of recent virtual-to-physical address translations) are "warm" for whichever task was just running — full of its data, its instructions, its address translations. The instant a different task takes over, that cached state is irrelevant, and the new task runs against **cold caches**, incurring a burst of cache misses and TLB misses that themselves cost far more cycles than the register swap that triggered them. This is why excessive context switching degrades performance in a way that doesn't show up as "the CPU is busy doing register saves" — it shows up as the CPU spending more cycles waiting on memory because it keeps losing its warm working set.

⚠️ **Warning:** Exact context-switch cost in cycles or microseconds is CPU-generation-, cache-topology-, and kernel-version-dependent. Don't cite a specific number from memory; the point to internalize is the _shape_ of the cost (fixed register-save cost + variable, often larger, cache-cold penalty), not a memorized figure.

**Common production causes of excessive context switching:**

- **Too many runnable threads/processes competing for too few cores** — the scheduler is forced to time-slice aggressively, switching far more often than the workload's actual parallelism justifies.
- **Lock contention** — a thread blocking on a mutex is taken off the CPU (voluntary context switch) and another thread is scheduled in; heavy contention on a hot lock produces a cycle of threads repeatedly blocking and being switched in and out, each switch paying the cold-cache tax described above.
- **Excessive I/O-driven wakeups** — a thread that blocks on I/O very frequently (small, chatty reads/writes) forces a context switch on every block, rather than doing larger batches of work per scheduling turn.

## 6. CPU Scheduling, Extended From [§10](./Section-10-Part2-Kernel-Components.md)

`[§10](./Section-10-Part2-Kernel-Components.md)` established CFS's core idea — pick the runnable task with the least virtual runtime — and named the scheduling classes only briefly. This section fills in the mechanics that matter for latency-sensitive and multi-core production systems.

**Preemption:** the scheduler does not wait politely for a running task to voluntarily give up the CPU. A running task can be preempted — forcibly switched out — whenever:

- A hardware timer interrupt (the periodic "scheduler tick") fires and the scheduler decides, based on accumulated virtual runtime, that a different task now deserves the CPU more.
- A higher-priority task becomes runnable — most sharply, a `SCHED_FIFO`/`SCHED_RR` real-time task waking up will always preempt a `SCHED_NORMAL` (CFS) task, because real-time classes are designed to guarantee latency bounds that fairness-based CFS scheduling cannot.
- The running task itself blocks (e.g., on I/O, a lock, or a syscall that must wait) — this is a **voluntary** context switch, as distinct from the involuntary preemption cases above.

**Real-time scheduling classes** (introduced briefly in `[§10](./Section-10-Part2-Kernel-Components.md)`, expanded here): `SCHED_FIFO` runs a task to completion (or until it blocks or yields) with no time-slicing against tasks of equal or lower priority at all; `SCHED_RR` is the same idea with a fixed round-robin time quota among equal-priority real-time tasks. Both always preempt ordinary `SCHED_NORMAL` tasks. They exist for genuinely latency-sensitive workloads — audio processing, industrial control loops, certain trading and telecom systems — where a bounded, predictable worst-case latency matters more than overall system fairness. They are used sparingly and deliberately in production because a real-time task that never blocks and never yields can starve everything else on that core, including the kernel's own housekeeping work.

**CPU affinity:** the ability to pin a process or thread to a specific core (or set of cores), via `taskset` or the `sched_setaffinity()` syscall, overriding the scheduler's free choice of core. Pinning trades scheduler flexibility for cache locality and predictability — a pinned task keeps its warm caches on one core instead of migrating and going cold, which is exactly the cost 5 described.

**NUMA-awareness (concept level):** on multi-socket servers, memory is **Non-Uniform Memory Access** — each CPU socket has faster access to its own local RAM than to RAM physically attached to a different socket. A NUMA-aware scheduler and memory allocator try to keep a task running on a core whose local memory already holds that task's data, because scheduling a task onto a "remote" NUMA node forces it to pay a real, measurable memory-latency penalty on every access, on top of any context-switch cost. Full NUMA tuning is out of scope here; the concept-level takeaway is that "which core" is not a scheduling detail that only affects fairness — on NUMA hardware it affects raw memory-access latency too.

## 7. Hands-On: Watching Interrupts and Context Switches

### 7.1 `vmstat` — Reading `cs` and `in`

**Purpose:** Report a rolling summary of CPU, memory, I/O, and scheduling activity at a fixed interval — the fastest single command for spotting an interrupt or context-switch anomaly without reaching for specialized tooling.

**Syntax:**

```bash
vmstat [interval] [count]
```

**Key columns for this section:**

| Column              | Meaning                                                                                                                                      |
| ------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| `cs`                | Context switches per second, system-wide                                                                                                     |
| `in`                | Interrupts per second, system-wide (excluding the clock/timer interrupt)                                                                     |
| `r`                 | Number of runnable processes waiting for CPU — high `r` alongside high `cs` suggests scheduler contention, not just legitimate parallel work |
| `us`/`sy`/`id`/`wa` | Time in userspace / kernel (syscalls, ISRs, scheduling) / idle / waiting on I/O                                                              |

**Example usage and expected output:**

```bash
$ vmstat 1 5
procs -----------memory---------- ---swap-- -----io---- -system-- ------cpu-----
 r  b   swpd   free   buff  cache   si   so    bi    bo   in    cs us sy id wa st
 2  0      0 214839  18204 421388    0    0     2     5   410   620  8  2 90  0  0
 9  0      0 213902  18204 421388    0    0     0     0  9820 48210 22 41  4 33  0
 8  0      0 213511  18204 421388    0    0     0     0  9640 47990 21 40  5 34  0
```

**How to read this:** The first sampled line reflects activity since boot and is conventionally discarded. Compare the steady-state lines: `cs` jumping from ~620 to ~48,000 per second, alongside `sy` (kernel time) climbing to ~40% and `r` staying elevated, is the classic signature of excessive context switching — the kernel is spending a large share of its time just swapping tasks in and out rather than doing useful work, exactly the cold-cache tax described in 5. A simultaneous jump in `in` points toward interrupt load as a contributing cause rather than pure scheduler contention from too many runnable threads.

**Production usage example:** A service reports elevated request latency with CPU utilization that "looks fine" in a coarse dashboard (say, 60% average). `vmstat 1` run during the incident window shows `cs` an order of magnitude above baseline — that's the signal to stop looking at raw CPU% and start asking _why_ the scheduler is switching so often: too many threads for the available cores, lock contention (5), or an interrupt storm (below).

**Common errors:** Reading the first output line as steady-state (it reflects since-boot averages, not the current interval); treating `in`/`cs` in isolation without cross-checking `sy` and `r` — a high `cs` on an otherwise idle, low-`sy` box may simply reflect a workload with many short-lived, legitimately independent tasks rather than a problem.

### 7.2 `cat /proc/interrupts` — Per-CPU Interrupt Counts by Device

**Purpose:** Show, per CPU core, how many interrupts each device/IRQ line has generated since boot — the direct tool for confirming _which_ device is the source when `vmstat`'s `in` column looks abnormal.

```bash
$ cat /proc/interrupts | head -8
           CPU0       CPU1       CPU2       CPU3
  16:    8942011      12044       9887      10230   IO-APIC   16-fasteoi   ahci
  24:      88213   14210044      91020      88012   IO-APIC   24-fasteoi   eth0
  NMI:        42         39         41         40   Non-maskable interrupts
 LOC:    9921038    9918820    9917654    9920112   Local timer interrupts
```

A device whose interrupt count is heavily skewed toward one core and is climbing far faster than the others (`eth0` above, concentrated almost entirely on `CPU1`) is the concrete evidence of an **interrupt storm** — covered next.

## 8. Synthesis Diagram: Interrupt → Bottom Half → Scheduler → Context Switch

```text
 Device signals CPU (hardware interrupt)
        │
        ▼
 TOP HALF (ISR) — minimal, fast, interrupts often disabled
        │
        ▼
 Deferred? ──► BOTTOM HALF (softirq / tasklet / workqueue) does the real work
        │
        ▼
 Scheduler tick / wakeup evaluates: does a different task now deserve the CPU?
        │
        ├── No  ──► interrupted task resumes exactly where it left off
        │
        └── Yes ──► CONTEXT SWITCH:
                       save outgoing task's registers + (maybe) page-table base
                       load incoming task's registers + (maybe) page-table base
                       incoming task runs — against cold caches (5)
```

This is the single mental model this section builds toward: an interrupt does not just "handle a device" — it is a potential trigger point for the scheduler to reconsider what runs next, and every such reconsideration that results in a switch carries the cache-cold cost described above. A device generating interrupts far more often than the work it represents justifies is therefore not just "noisy" — it is directly forcing extra scheduling overhead on top of its own handling cost.

## 9. Production Relevance: Interrupt Storms and Context-Switch Overhead

Two closely related failure patterns show up repeatedly in real incidents, and both are fully developed with tooling and runbooks in Part 11 ([§80](../Part11/Section-80-Part11-Performance-Fundamentals-Unified-Model.md)–[§88](../Part11/Section-88-Part11-Incident-Case-Studies.md)):

- **Interrupt storms** — a misbehaving or misconfigured device (a failing NIC, a disk controller stuck retrying, a driver bug) generates interrupts far faster than legitimate traffic justifies. Because ISRs run with interrupts effectively disabled on the handling core, a storm can starve that core almost entirely — the scheduler barely gets to run anything else on it, `in` in `vmstat` spikes, and `/proc/interrupts` shows one IRQ line dominating one core's count. The fix is usually driver/firmware-level (a known buggy NIC driver, a failing disk needing replacement) or, as a mitigation, spreading interrupt load across cores via **IRQ affinity** tuning (`/proc/irq/N/smp_affinity`) rather than leaving every interrupt pinned to one core.
- **Excessive context-switch overhead** — an application-level pattern (thread-per-connection servers under heavy load, lock contention in a hot path, an overly chatty I/O pattern) drives `cs` far above baseline, with the cold-cache tax from 5 showing up as elevated `sy` time and degraded throughput despite CPU not looking "pegged" in a coarse view. The fix is architectural — reducing thread count relative to cores, using event-driven/async I/O instead of thread-per-request, reducing lock granularity, or applying CPU affinity/pinning to keep hot threads cache-warm — not something `nice`/`renice` alone can resolve.

Full incident methodology, thresholds, and case studies for both patterns live in Part 11 ([§80](../Part11/Section-80-Part11-Performance-Fundamentals-Unified-Model.md)–[§88](../Part11/Section-88-Part11-Incident-Case-Studies.md)); this section's job is to make sure the underlying mechanism — why an interrupt or a switch costs what it costs — is understood before reaching for those runbooks.

## 10. Common Misconceptions

1. **"Interrupts and syscalls are unrelated mechanisms."** False — both are traps into the same CPU trap/exception hardware facility (3); a syscall is a _software_-triggered trap the running program initiates deliberately, a hardware interrupt is an _externally_ triggered trap a device initiates asynchronously. `[§11](./Section-11-Part2-System-Calls-Kernel-Userland-Boundary.md)`'s syscall trap and this section's ISR dispatch share the same underlying "suspend, consult a table, jump to a handler" shape.
2. **"More CPU cores always reduce context-switch overhead."** Not necessarily — more cores reduce contention only if the workload's actual parallelism scales with them. A workload with heavy lock contention on a single shared resource, or a fixed number of chatty, interdependent threads, can produce just as much context-switch churn on 64 cores as on 8, because the bottleneck is the _coordination pattern_, not raw core count. Adding cores can even increase cross-core cache-coherence traffic in some contended workloads.
3. **"High CPU utilization and high context-switch rate mean the same thing."** They're different signals — a box can show low aggregate `us`/`sy` utilization while still suffering from excessive switching overhead relative to the _useful_ work being done per switch, which is exactly why `cs` and `in` are read alongside CPU% in 7, not as a substitute for it.
4. **"The top half of an interrupt handler does the real work."** Backwards — the top half is deliberately minimal by design; the bottom half (softirq/tasklet/workqueue) is where the substantive work happens, precisely so the top half doesn't block other interrupts and scheduling decisions on that core (4).

## 11. Tiered Interview Questions

**🎯 Beginner:** _"What is a context switch, and why does it have a cost beyond just saving and restoring registers?"_
**Model answer:** A context switch is when the kernel changes which process or thread is actually running on a CPU core — it saves the outgoing task's register state and loads the incoming task's previously saved state. The register save/restore itself is fast and fixed-cost, but the bigger cost is indirect: the CPU's caches and TLB were "warm" for the task that just got switched out, full of its data and address translations. The new task starts running against cold caches, so it incurs a burst of cache misses that cost more cycles than the register swap itself.
_What the interviewer is probing for:_ whether the candidate knows the cost is dominated by cache effects, not the mechanical register swap — a very common surface-level gap.

**🎯 Intermediate:** _"Explain the top half / bottom half split in interrupt handling and why it exists."_
**Model answer:** An interrupt service routine (top half) runs with interrupts disabled or reduced on that core, so anything it does blocks other interrupts and scheduling decisions from happening promptly on that core. The kernel splits handling into a fast top half that does only the urgent minimum — acknowledge the device, grab critical data before it's overwritten — and defers the rest to a bottom half (softirq, tasklet, or workqueue) that runs shortly after with interrupts re-enabled. This keeps any single device's interrupt handling from starving the rest of the system, which matters a lot for high-interrupt-rate devices like NICs.
_What the interviewer is probing for:_ real understanding of _why_ the split matters operationally, not just naming the two halves.

**🎯 Senior:** _"A production host shows `vmstat`'s `cs` column at 10x its normal baseline, but CPU utilization looks moderate. How do you investigate, and what are the likely root causes?"_
**Model answer:** I'd first check `/proc/interrupts` to rule out an interrupt storm — a device dominating one core's interrupt count — since that alone can drive up both `in` and, indirectly, `cs`. If interrupts look normal, I'd suspect an application-level pattern: too many runnable threads relative to cores causing the scheduler to time-slice aggressively, or lock contention where threads are repeatedly blocking and being rescheduled. I'd look at `r` in `vmstat` for excess runnable-but-waiting threads, and use per-process thread counts and, if needed, a profiler to identify contended locks. The key point is that moderate CPU utilization with high `cs` isn't a contradiction — it means a large share of the CPU time being spent is going into scheduling overhead and cold-cache penalties rather than useful work, so the fix is architectural (reduce thread count, reduce lock granularity, consider affinity) rather than adding more cores.
_What the interviewer is probing for:_ ability to reason from a metric anomaly to a root-cause hypothesis using the right tools in the right order, not just naming `vmstat` and stopping there.

**🎯 Architect:** _"You're designing a low-latency trading system on Linux. How would you use CPU affinity, real-time scheduling classes, and IRQ tuning together, and what are the risks of each?"_
**Model answer:** I'd isolate a set of cores from the general scheduler (kernel `isolcpus`-style isolation, verified against current kernel documentation) and pin the latency-critical threads to those cores with CPU affinity, keeping their working set cache-warm and avoiding migration-driven cold-cache penalties. For threads with hard latency requirements, I'd consider `SCHED_FIFO` to guarantee they preempt ordinary work immediately — but only for a small, carefully audited set of threads, because a real-time thread that misbehaves (an unexpected infinite loop, a missed yield) can starve everything else on that core, including kernel housekeeping, which is a severe availability risk. I'd also steer device interrupts away from the isolated cores via IRQ affinity tuning, so an interrupt storm on a NIC or disk controller can't intrude on the isolated latency-critical cores at all. The overall risk profile is that every one of these techniques trades general-purpose flexibility and fairness for deterministic behavior on a narrow slice of the system — which is the right tradeoff for this workload, but each piece (real-time priority, core isolation, IRQ steering) needs monitoring and a rollback plan, because a mistake in any of them tends to fail as an availability incident, not a graceful degradation.
_What the interviewer is probing for:_ synthesis across affinity, real-time scheduling, and interrupt routing as a coherent system design, plus explicit acknowledgment of the risk each technique introduces — not just listing the tools.

## 12. 🔑 Key Takeaways

- Interrupts and syscalls both use the same underlying CPU trap mechanism from `[§11](./Section-11-Part2-System-Calls-Kernel-Userland-Boundary.md)` — a hardware interrupt is device-triggered and asynchronous; a syscall is a software interrupt the running program triggers deliberately.
- The CPU dispatches interrupts via a table (the IDT on x86) to a registered Interrupt Service Routine (ISR); the kernel splits handling into a fast, minimal **top half** and a deferred **bottom half** (softirq/tasklet/workqueue) specifically so slow handling of one device doesn't starve interrupts and scheduling on that core.
- A context switch's real cost is dominated by **cold-cache effects** (L1/L2/TLB misses after the switch), not the register save/restore itself — this is why excessive switching degrades throughput in ways that don't show up as raw "CPU busy" time.
- `[§10](./Section-10-Part2-Kernel-Components.md)`'s CFS model is extended here with **preemption** (timer-tick reevaluation, real-time tasks always preempting `SCHED_NORMAL`), **real-time scheduling** (`SCHED_FIFO`/`SCHED_RR`, used sparingly and deliberately), **CPU affinity** (pinning for cache locality), and **NUMA-awareness** (keeping tasks near their local memory on multi-socket hardware).
- `vmstat 1`'s `cs` and `in` columns, cross-referenced with `/proc/interrupts`, are the fastest way to detect and localize both interrupt storms and excessive context-switch overhead — two genuinely common, distinct production incident patterns, fully developed with runbooks in Part 11 ([§80](../Part11/Section-80-Part11-Performance-Fundamentals-Unified-Model.md)–[§88](../Part11/Section-88-Part11-Incident-Case-Studies.md)).
- More cores do not automatically reduce context-switch overhead — contention from lock design or coordination patterns can persist (or worsen) regardless of core count.
