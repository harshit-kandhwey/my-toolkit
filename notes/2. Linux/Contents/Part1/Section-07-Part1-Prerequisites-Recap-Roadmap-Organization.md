# Section 7 (Part 1): Prerequisites Recap and How This Roadmap Is Organized

## 1. What You Need Before Continuing

Nothing beyond general computer literacy is required to proceed — this project builds every additional prerequisite in place, as it becomes relevant, rather than assuming it upfront:

- **Basic networking concepts** (IP addresses, DNS, routing) will be briefly recapped at the start of Part 7 ([§51](../Part7/Section-51-Part7-Networking-Fundamentals-Recap.md)) before diving into Linux-specific networking tools (`ip`, `ss`, firewalls, SSH).
- **Command-line comfort** will be built progressively starting in Part 3 ([§17](../Part3/Section-17-Part3-Filesystem-Hierarchy-Standard.md)), where the first sustained hands-on command sequences appear, using the same full command-documentation template [§1](./Section-01-Part1-What-Linux-Is-Kernel-vs-OS-vs-Distribution.md)–[§4](./Section-04-Part1-Linux-Philosophy-Design-Principles.md) already demonstrated (`uname`, `hostnamectl`, `modinfo`, the `grep | awk | sort | uniq -c | sort -rn | head` pipeline, and more).
- **No prior Linux experience is assumed.** [§1](./Section-01-Part1-What-Linux-Is-Kernel-vs-OS-vs-Distribution.md)–[§6](./Section-06-Part1-Where-Linux-Runs-Today.md) deliberately front-loaded the conceptual vocabulary (kernel vs. distro, licensing, philosophy, distro families, deployment landscape) specifically so that Part 2 onward can build hands-on material on a shared mental model instead of re-explaining first principles mid-command.

This repo's `INDEX.md`/`README.md` will formalize navigation further as more parts land, but three usage patterns are already supported by the structure established in [§1](./Section-01-Part1-What-Linux-Is-Kernel-vs-OS-vs-Distribution.md)–[§6](./Section-06-Part1-Where-Linux-Runs-Today.md):

## 4. Interview Questions (Meta-Section)

**🎯 Beginner:** _"If you were mentoring a junior engineer with zero Linux experience, in what order would you have them learn it, and why?"_
**Model answer:** I'd start with the conceptual vocabulary before any hands-on commands — what the kernel is versus a distribution, and the "everything is a file / small composable tools" philosophy — because those ideas explain _why_ later commands and config formats look the way they do, rather than leaving the learner to memorize syntax with no mental model. From there I'd move to the filesystem and permissions (since almost every other topic assumes you can navigate and reason about file ownership), then processes and shell scripting, then networking, then package management and systemd, saving performance tuning, security hardening, and automation for once the fundamentals are solid. Interview prep and advanced production scenarios come last, once there's enough real material to actually reason about.
_What the interviewer is probing for:_ whether the candidate can structure a learning plan around dependency order and conceptual scaffolding, not just list topics — a proxy for how they'd onboard a new hire in real life.

**🎯 Intermediate:** _"This roadmap embeds interview questions inside every technical section instead of only at the end. What's the argument for that, versus a single dedicated interview-prep module?"_
**Model answer:** Embedding questions next to the material they test keeps the question grounded in freshly-explained context — you immediately see how a concept like GPLv2 derivative-work boundaries ([§3](./Section-03-Part1-Open-Source-Licensing-GPL-Governance.md)) gets turned into a senior-level question, rather than encountering the question cold, weeks later, disconnected from the explanation. It also reinforces the material twice, at different cognitive levels (explain it, then defend/apply it under interview framing). A dedicated final module (Part 16, [§116](../Part16/Section-116-Part16-Beginner-Level-Question-Bank.md)–[§122](../Part16/Section-122-Part16-Hiring-Manager-Behavioral-Technical-Crossover-Questions.md)) still has real value on top of that — it lets you drill breadth and difficulty progression across the entire roadmap in one pass right before an actual interview, and organizes by scenario type rather than topic. The two aren't redundant; embedded questions build understanding, the consolidated bank builds recall and speed.
_What the interviewer is probing for:_ whether the candidate thinks about learning-design trade-offs, not just Linux content — relevant for senior engineers who end up mentoring or building onboarding material themselves.

**🎯 Senior:** _"Part 1 of this roadmap spent seven sections on history, licensing, and philosophy before a single filesystem command. Is that a good use of a new engineer's time, or front-loaded overhead that should be trimmed?"_
**Model answer:** It's a deliberate investment, not overhead, provided it stays as tight as [§1](./Section-01-Part1-What-Linux-Is-Kernel-vs-OS-vs-Distribution.md)–[§6](./Section-06-Part1-Where-Linux-Runs-Today.md) kept it — each of those sections still included hands-on commands (`uname`, `modinfo`, the auth-log pipeline) and interview-relevant material, not pure trivia. The payoff shows up constantly later: knowing _why_ config is plain text ([§4](./Section-04-Part1-Linux-Philosophy-Design-Principles.md)) means `/etc/fstab` and systemd unit files never feel arbitrary; knowing the kernel/distro split ([§1](./Section-01-Part1-What-Linux-Is-Kernel-vs-OS-vs-Distribution.md)) means CVE triage and patch management ([§89](../Part12/Section-89-Part12-Linux-Security-Model-Recap-Threat-Landscape.md), [§94](../Part12/Section-94-Part12-Vulnerability-Patch-Management.md)) make sense on first exposure instead of needing re-explanation; knowing GPLv2's derivative-work boundary ([§3](./Section-03-Part1-Open-Source-Licensing-GPL-Governance.md)) means a licensing question in a real commercial-appliance project doesn't require starting from zero. The risk would be if "foundations" ballooned into unfocused trivia with no operational payoff — that's the failure mode to guard against, not the existence of a foundations part itself. Given how tightly [§1](./Section-01-Part1-What-Linux-Is-Kernel-vs-OS-vs-Distribution.md)–[§6](./Section-06-Part1-Where-Linux-Runs-Today.md) tied history and philosophy back to concrete commands and production scenarios, the time is well spent.
_What the interviewer is probing for:_ judgment about learning-content design and the ability to defend a structural choice on its actual merits rather than either dismissing "soft" foundational material or defending it reflexively.

## 5. Common Misconceptions (Part 1 Summary)

Synthesizing the strongest, most interview-relevant misconceptions established across [§1](./Section-01-Part1-What-Linux-Is-Kernel-vs-OS-vs-Distribution.md)–[§6](./Section-06-Part1-Where-Linux-Runs-Today.md):

1. **"Linux is a fork of Unix."** False — no AT&T or BSD Unix source code exists inside the Linux kernel. Linux is a from-scratch reimplementation of Unix's design principles and largely its POSIX system-call interface, written independently starting in 1991. "Unix-like" is the technically correct term; "Unix" itself is a trademark with formal certification requirements Linux distributions have generally never pursued ([§2](./Section-02-Part1-History-and-Evolution.md)).
2. **"GNU/Linux and Linux are different operating systems."** They are not. "Linux," strictly, is the kernel; "GNU/Linux" is a naming convention some communities (notably the FSF and Debian) use to explicitly credit the GNU Project's userland contributions (compiler, shell, core utilities) alongside the kernel. Same underlying system, different naming emphasis ([§1](./Section-01-Part1-What-Linux-Is-Kernel-vs-OS-vs-Distribution.md), [§2](./Section-02-Part1-History-and-Evolution.md)).
3. **"If my proprietary application runs on Linux, I have to open-source it."** False, and the single highest-value misconception to get right. GPLv2's copyleft obligations attach to **derivative works of GPL-licensed code itself** — code that incorporates or is compiled into GPL-licensed source, or a kernel module tightly coupled to kernel internals. An application that merely runs on top of the kernel, talking to it only through the stable, published system-call interface, is not a derivative work and carries no source-disclosure obligation. This is precisely why commercial, closed-source software runs on Linux at massive scale without being open-sourced ([§3](./Section-03-Part1-Open-Source-Licensing-GPL-Governance.md)).
4. **"All Linux distributions behave identically once you know one."** False in practice — init systems, package managers, default security modules (SELinux vs. AppArmor), release cadence (rolling vs. point release), and filesystem/config layout conventions vary meaningfully across the Debian, RHEL, SUSE, Arch, and Alpine families. Two distros running the identical kernel version can still diverge in behavior due to distro-specific patches and build configuration ([§1](./Section-01-Part1-What-Linux-Is-Kernel-vs-OS-vs-Distribution.md), [§5](./Section-05-Part1-Major-Distribution-Families.md)).
5. **"Open source means unsupported" / "GPL means free of charge."** Enterprise distributions (RHEL, SLES, Ubuntu Pro) sell paid, contractual support with defined SLAs on top of open-source code — open licensing and commercial support are not mutually exclusive, and the GPL explicitly permits charging money for distribution; it only protects the recipient's downstream freedoms ([§3](./Section-03-Part1-Open-Source-Licensing-GPL-Governance.md), [§5](./Section-05-Part1-Major-Distribution-Families.md)).
6. **"A newer kernel version string always means more patched/secure."** Not necessarily — distro vendors backport security fixes into their own kernel builds independently of upstream version numbers, so patch exposure must be judged against the vendor's own security advisory (RHSA, USN, etc.), not the raw `uname -r` string alone ([§1](./Section-01-Part1-What-Linux-Is-Kernel-vs-OS-vs-Distribution.md)).
7. **"Unix philosophy means avoiding all abstraction and refusing to build bigger tools."** False — the philosophy is about composability and single responsibility, not about refusing scale. `systemd`, Kubernetes, and modern package managers are large, sophisticated systems that still honor the philosophy by exposing composable, scriptable, text-based interfaces rather than becoming opaque monoliths ([§4](./Section-04-Part1-Linux-Philosophy-Design-Principles.md)).
8. **"Containers are a separate invention from core Linux."** False — Docker/Kubernetes did not invent a new OS model; they composed pre-existing kernel primitives (`chroot`, namespaces, cgroups, OverlayFS) the same way a shell pipeline composes small tools, and expose plain-text Dockerfiles/YAML manifests as a direct continuation of the "transparency over hidden magic" principle ([§4](./Section-04-Part1-Linux-Philosophy-Design-Principles.md), forward-referenced fully at [§99](../Part13/Section-99-Part13-Linux-Foundation-For-Containers-Namespaces-Cgroups-Chroot-Overlayfs.md)).
9. **"Distro choice is mainly a technical/taste decision."** In enterprise settings it's driven far more by support lifecycle, compliance certification availability, ecosystem compatibility, and existing organizational expertise than by any inherent technical superiority of one distro over another ([§5](./Section-05-Part1-Major-Distribution-Families.md)).

## 6. Part 1 🔑 Key Takeaways Checklist

```text
□ Linux, strictly, is the kernel; a distribution is the kernel + userland + package manager
  + support model, packaged and branded (§1)
□ The layering is Hardware → Kernel → Userland/System Software → Applications, and
  uname -r + /etc/os-release (or hostnamectl) together fully characterize a host (§1)
□ Linux descends conceptually from Unix (1969) via BSD and the AT&T/System V split;
  the GNU Project (1983) built nearly a full free OS but lacked a working kernel;
  Torvalds' kernel (1991), relicensed under the GPL in 1992, completed it (§2)
□ Linux is a from-scratch reimplementation of Unix/POSIX concepts, not a fork of
  Unix source code — "Unix-like" is the precise term (§2)
□ The Linux kernel is GPLv2-licensed (copyleft); obligations trigger on distributing
  a derivative work, not on private use or on software that merely runs atop the kernel (§3)
□ Kernel governance is layered: Torvalds holds the trademark and final mainline authority;
  the Linux Foundation is a neutral funding/infrastructure body with no technical control;
  a maintainer hierarchy (documented in MAINTAINERS) does the actual patch review via
  mailing lists and git send-email, not GitHub PRs (§3)
□ Five inherited design principles explain nearly every later convention: everything is
  a file, small composable tools, text streams as a universal interface, transparency
  over hidden magic, and multi-user/multi-tasking by design (§4)
□ Ignoring the philosophy has predictable costs: monolithic unmaintainable scripts,
  undiffable opaque binary config, and root-everywhere permission shortcuts that remove
  blast-radius containment (§4)
□ Major distro families — Debian-based (apt), RHEL-based (dnf/yum), SUSE-based (zypper),
  independent/rolling (Arch, pacman), container-minimalist (Alpine, apk/musl) — differ
  meaningfully in packaging, release cadence, and target use case, not just branding (§5)
□ Enterprise distro choice is driven by support lifecycle and compliance certification
  more than by raw technical preference (§5)
□ Linux dominates public cloud VM/container infrastructure, the majority of public web
  serving, mobile (via the Android kernel), supercomputing (TOP500), and is the kernel
  underneath Docker/Kubernetes via namespaces and cgroups (§6)
□ Specific market-share and version numbers shift over time and by measurement
  methodology — verify current figures rather than citing a fixed remembered number (§6)
```
