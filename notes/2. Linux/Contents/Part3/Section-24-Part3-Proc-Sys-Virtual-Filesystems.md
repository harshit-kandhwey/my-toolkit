# Section 24 (Part 3): /proc and /sys Virtual Filesystems for Introspection

## 1. What a Virtual Filesystem Actually Is

Every filesystem covered so far in this Part — ext4, XFS (§18), and the general inode model (§19) — shares one property: there is real data sitting on a real disk, and the filesystem's job is organizing and locating those bytes. `/proc` and `/sys` break that assumption entirely. Both are **pseudo-filesystems** (also called virtual filesystems): they have no disk backing whatsoever. Every file, directory, and byte of content under them is **generated by the kernel on the fly**, the moment something reads it, from live in-memory kernel data structures — not stored anywhere, not persisted across reboots, and not occupying disk space no matter how large `cat /proc/meminfo` looks.

This matters practically in ways that trip people up:

- **`ls -la /proc/cpuinfo` reports a size of 0 bytes** (or a small placeholder value) even though `cat`-ing it produces a full page of text — the kernel doesn't know the content's length until it actually generates it, because there's no stored file to `stat()` in the normal sense.
- **Nothing under `/proc` or `/sys` survives a reboot**, because there's nothing to survive — it's regenerated from scratch as the kernel and running processes come back up. This is fundamentally different from a config file surviving a reboot because it's written to disk.
- **Both are still real filesystems from userspace's point of view** — they're mounted (§20's mounting/fstab coverage applies structurally, even though there's no block device involved), they appear in `mount` output, and every standard tool (`cat`, `ls`, `grep`, `echo >`) works against them exactly as it would against ext4 files, because the **VFS layer** (§10, Part 2's kernel-components coverage) abstracts the difference away — VFS doesn't care whether the underlying filesystem driver serves bytes from disk blocks or synthesizes them from kernel memory on the spot.

> 💡 **Tip:** The single mental model that makes both filesystems make sense: `/proc` and `/sys` are not places where data is _stored_ — they are places where the kernel's internal state is made _readable_ (and in many cases _writable_) through the ordinary file-and-directory interface every Unix tool already knows how to use. Reading a file under either tree is really a function call into the kernel wearing a filename as a disguise.

`/proc` and `/sys` both appear in §17's FHS listing as standard, mandatory mount points — this section is where that listing gets its actual depth.

## 2. /proc: Process and Kernel Information

`procfs` is the older of the two, originally designed around exposing **per-process information** — hence the name — and later grew to also expose assorted kernel-wide state that didn't have a better home at the time. It's mounted at `/proc` on essentially every Linux system, no exceptions in normal operation.

### 2.1 Per-Process: `/proc/[pid]/`

Every running process on the system has a directory `/proc/<pid>/` containing a live view of that process's kernel-tracked state. This is the mechanism that tools like `ps`, `top`, and `htop` (§35, Part 5) are built on top of — they are not doing anything privileged or special; they are reading the same files available to any user with permission.

Selected entries worth knowing by name:

| Path                  | Contents                                                                                                                    |
| --------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| `/proc/[pid]/status`  | Human-readable process state summary — name, PID/PPID, state (running/sleeping/zombie), memory usage, UID/GID, signal masks |
| `/proc/[pid]/cmdline` | The exact command-line arguments the process was launched with (NUL-separated)                                              |
| `/proc/[pid]/environ` | The process's environment variables at exec time (NUL-separated; readable only by the owning user or root)                  |
| `/proc/[pid]/fd/`     | A directory of symlinks, one per open file descriptor, each pointing at the file/socket/pipe it refers to                   |
| `/proc/[pid]/cwd`     | Symlink to the process's current working directory                                                                          |
| `/proc/[pid]/exe`     | Symlink to the actual executable binary backing the process                                                                 |
| `/proc/[pid]/maps`    | The process's virtual memory mappings — libraries, heap, stack, each with address range and permissions                     |
| `/proc/[pid]/limits`  | The effective resource limits (`ulimit`-style) currently applied to the process                                             |

**Production usage example:** `/proc/[pid]/fd/` is the fastest way to answer "what files/sockets does this stuck process actually have open right now" during an incident, without needing `lsof` installed — `ls -l /proc/<pid>/fd/` shows every descriptor as a symlink, immediately revealing things like a deleted log file still being held open (§19's "deleted but still consuming space" scenario resolves through exactly this path) or a socket connected to an unexpected remote host.

```bash
$ ls -l /proc/1234/fd/
lrwx------ 1 app app 64 Jul 26 10:02 0 -> /dev/pts/0
lrwx------ 1 app app 64 Jul 26 10:02 1 -> /dev/pts/0
l-wx------ 1 app app 64 Jul 26 10:02 3 -> /var/log/app.log (deleted)
lrwx------ 1 app app 64 Jul 26 10:02 4 -> socket:[891234]
```

The `(deleted)` annotation on fd 3 above is exactly the signature of an unlinked-but-still-open file from §19 — `stat`-ing that fd path still reports the live inode and its current size, which is how you'd confirm disk space is being held by this specific process before deciding whether to restart it.

### 2.2 System-Wide: Selected Top-Level Files

`/proc` also exposes kernel- and system-wide state as flat files directly under `/proc/`, not scoped to any one PID:

| Path            | Contents                                                                                                                                          |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| `/proc/cpuinfo` | Per-logical-CPU details — model, flags, core/thread topology                                                                                      |
| `/proc/meminfo` | System memory breakdown — total, free, buffers, cache, swap (§16's virtual-memory coverage, and §82 in Part 11, both build on this file directly) |
| `/proc/loadavg` | The 1/5/15-minute load averages plus running/total process counts — what `uptime` reads                                                           |
| `/proc/version` | Kernel version string and build info                                                                                                              |
| `/proc/mounts`  | The live, currently-mounted filesystem table — the real-time equivalent of `/etc/fstab`'s static configuration (§20)                              |
| `/proc/cmdline` | The kernel boot command line the running kernel was actually started with (§12, Part 2)                                                           |
| `/proc/uptime`  | System uptime and idle time, in seconds                                                                                                           |

```bash
$ cat /proc/loadavg
0.42 0.38 0.31 2/487 18213
```

Reading left to right: 1-, 5-, and 15-minute load averages, then `running/total` process counts, then the most recently created PID on the system.

> 💡 **Tip:** `/proc/mounts` is the source of truth for what's actually mounted right now — `/etc/fstab` (§20) only describes what _should_ be mounted at boot or on `mount -a`, and the two can legitimately diverge (a manual `mount`/`umount`, a failed boot-time mount, a bind mount created ad hoc). When troubleshooting "why does this path behave like it's not mounted," trust `/proc/mounts` over `/etc/fstab`.

## 3. /sys: The Device and Driver Model

`sysfs`, mounted at `/sys`, was introduced later than `/proc`, specifically to expose the kernel's **device and driver model** — the structured, hierarchical representation of every device, driver, bus, and class the kernel knows about — in a clean, purpose-built way that `/proc` was never designed to do well.

Where `/proc` grew organically and ended up as a mix of process info and miscellaneous kernel state with no strong internal consistency, `/sys` is deliberately structured around the kernel's actual internal object model: each directory under `/sys` corresponds to a real kernel object (a `struct device`, `struct driver`, and so on), and the filesystem hierarchy mirrors real relationships between those objects rather than being an arbitrary namespace.

Key top-level directories:

| Path             | Contents                                                                                                     |
| ---------------- | ------------------------------------------------------------------------------------------------------------ |
| `/sys/class/`    | Devices grouped by functional type regardless of bus (e.g., all network interfaces under one directory)      |
| `/sys/block/`    | Block devices — disks, partitions                                                                            |
| `/sys/bus/`      | Devices organized by the physical/logical bus they're attached to (PCI, USB, etc.)                           |
| `/sys/devices/`  | The canonical, complete device hierarchy — everything else in `/sys` is largely symlinks back into this tree |
| `/sys/module/`   | Currently loaded kernel modules and their parameters (§14, Part 2's `lsmod`/`modprobe` coverage)             |
| `/sys/firmware/` | Firmware-exposed data, including some ACPI/EFI information                                                   |

**Practical example — network interfaces:**

```bash
$ ls /sys/class/net/
eth0  lo

$ cat /sys/class/net/eth0/operstate
up

$ cat /sys/class/net/eth0/address
02:42:ac:11:00:02

$ cat /sys/class/net/eth0/mtu
1500
```

**Practical example — block devices:**

```bash
$ ls /sys/block/
sda  sdb  nvme0n1

$ cat /sys/block/sda/size
41943040
$ cat /sys/block/sda/queue/rotational
0
```

`/sys/block/sda/queue/rotational` reporting `0` is a standard scripted way to detect whether a block device is an SSD (`0`) or a spinning disk (`1`) without parsing `lsblk`/`smartctl` output — useful when a provisioning script needs to make an I/O-scheduler decision (§10, Part 2) based on underlying media type.

## 4. /proc vs. /sys: The Distinction That Actually Matters

Both are virtual, kernel-generated, non-persistent filesystems, which is enough to make them look interchangeable at a glance — they are not, and conflating them is the most common misconception about this pair (7).

| Dimension             | `/proc`                                                                                                                  | `/sys`                                                                          |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------- |
| Original purpose      | Per-process information                                                                                                  | Device and driver model exposure                                                |
| Introduced            | Earlier — a long-standing Linux fixture                                                                                  | Later — specifically to give devices/drivers a proper home                      |
| Internal structure    | Loosely organized; grew to include unrelated kernel-wide state over time                                                 | Deliberately structured to mirror the kernel's actual internal object hierarchy |
| Primary content today | `/proc/[pid]/*` process data, plus system-wide info files (`meminfo`, `cpuinfo`, etc.) and the `sysctl` tunable tree (5) | Devices, drivers, buses, classes, loaded kernel modules and their parameters    |
| Typical consumers     | `ps`, `top`, `free`, `uptime`, and most classic introspection tools                                                      | `udev`, hardware-detection tooling, device-specific scripts                     |

> ⚠️ **Warning:** Do not assume every piece of kernel state has "one obvious place" it lives. Historical accident, not clean design, put some overlapping information in both trees (module parameters, for instance, are reachable through both `/sys/module/` and older `/proc`-based mechanisms depending on the subsystem) — when in doubt, check both rather than assuming a fact you learned about `/proc`'s layout automatically tells you where the `/sys` equivalent lives, or vice versa.

## 5. sysctl and /proc/sys: Tunable Kernel Parameters

`/proc/sys/` is a specific, heavily operational subtree of `/proc` worth treating separately: it exposes **kernel parameters that can be read and, in most cases, written** — making it the live control surface for tuning kernel behavior without a reboot or a recompile. The `sysctl` command is the standard front end to this exact subtree; every `sysctl` parameter name maps directly onto a path under `/proc/sys/` with dots replaced by slashes (`net.ipv4.ip_forward` ⇄ `/proc/sys/net/ipv4/ip_forward`).

**Reading and writing directly:**

```bash
$ cat /proc/sys/net/ipv4/ip_forward
0
$ echo 1 > /proc/sys/net/ipv4/ip_forward
```

**The equivalent, and more commonly used, `sysctl` interface:**

```bash
$ sysctl net.ipv4.ip_forward
net.ipv4.ip_forward = 0

$ sysctl -a | head -5
kernel.ostype = Linux
kernel.osrelease = 6.8.0-generic
kernel.version = #1 SMP ...
vm.swappiness = 60
net.core.somaxconn = 4096
```

| Command                     | Effect                                                       |
| --------------------------- | ------------------------------------------------------------ |
| `sysctl -a`                 | List every currently readable kernel parameter and its value |
| `sysctl <param>`            | Read one parameter                                           |
| `sysctl -w <param>=<value>` | Write one parameter — **runtime-only**, lost on reboot       |
| `sysctl -p [file]`          | Reload parameters from a config file into the running kernel |

**The persistence distinction is the single most important operational fact here:** both direct writes to `/proc/sys/...` and `sysctl -w` change the **running kernel's in-memory state immediately**, but neither persists across a reboot. Permanent tuning belongs in `/etc/sysctl.conf` or a drop-in file under `/etc/sysctl.d/`, applied at boot (and reloadable on demand with `sysctl -p`).

```ini
# /etc/sysctl.d/99-custom.conf
net.ipv4.ip_forward = 1
vm.swappiness = 10
net.core.somaxconn = 8192
```

> ⚠️ **Warning:** A parameter changed with `sysctl -w` or a direct `echo` into `/proc/sys/` that isn't also persisted to `/etc/sysctl.d/` will silently revert on the next reboot — a frequent cause of "this fix worked, then came back after maintenance" incidents. If a `sysctl` change is meant to be permanent, it must exist in both places: applied now (for the live kernel) and written to a config file (for every future boot).

**Production relevance:** `sysctl`-tunable parameters are central to both performance work and security hardening — `vm.swappiness` and `net.core.somaxconn`-style tuning show up throughout Part 11's performance coverage (§80–§88), while kernel-hardening parameters (`net.ipv4.conf.all.rp_filter`, `kernel.dmesg_restrict`, and similar) are core material in Part 12's security section (§89–§96, specifically the sysctl-security-parameters subsection). This section is the mechanical foundation both of those later Parts assume is already understood.

## 6. Common Misconceptions

1. **"Files under `/proc` and `/sys` take up disk space proportional to their apparent content."** They take up none — nothing is stored; content is generated by the kernel at read time (1). The `0`-byte size `ls -la` often reports for `/proc` files is a visible symptom of this, not a bug.
2. **"`/proc` and `/sys` are basically the same thing with two names."** They overlap in being virtual and kernel-generated, but they differ sharply in purpose and structure — `/proc` is older and centered on process/general kernel info, `/sys` is newer and deliberately structured around the device/driver model (4). Treating them as interchangeable leads to looking in the wrong tree for a given piece of information.
3. **"Writing to `/proc/sys/...` or running `sysctl -w` makes a permanent change."** Both only affect the currently running kernel's in-memory state — the change is gone on reboot unless it's also written into `/etc/sysctl.conf` or a `/etc/sysctl.d/` drop-in file (5). This is a genuinely common production incident pattern, not a theoretical edge case.
4. **"Reading `/proc/[pid]/environ` or `/proc/[pid]/maps` on any process is fine for any user."** Access to another user's process internals through `/proc/[pid]/` is permission-gated — most of this detail is only visible to the owning user or root, which matters when scripting cross-user introspection tooling (full permission-model depth is Part 4, §25–§32).

## 7. Tiered Interview Questions

**🎯 Beginner:** _"What does it mean that `/proc` and `/sys` are 'virtual filesystems,' and how is that different from ext4 or XFS?"_
**Model answer:** ext4 and XFS store real data on a real disk — files exist as data blocks the kernel locates via inodes (§19) and persist across reboots. `/proc` and `/sys` have no disk backing at all; every file's content is generated by the kernel on the spot, the moment it's read, from live in-memory kernel state, and nothing under either tree survives a reboot because there's nothing stored to survive — it's regenerated from scratch. They still behave like normal filesystems to userspace tools because the VFS layer (§10) abstracts the difference away.
_What the interviewer is probing for:_ Whether the candidate understands "virtual" to mean "no disk backing, generated on demand," not just "special files with unusual names."

**🎯 Intermediate:** _"What's the actual difference between `/proc` and `/sys`, given that both are virtual and kernel-generated?"_
**Model answer:** `/proc` is older and originally purpose-built for per-process information (`/proc/[pid]/*`), later accumulating a fair amount of loosely organized system-wide state (`meminfo`, `cpuinfo`, and the `/proc/sys` tunable tree) without a strong unifying structure. `/sys` was introduced specifically to expose the kernel's device and driver model in a clean, hierarchical way that mirrors the kernel's actual internal object relationships — `/sys/class/`, `/sys/block/`, `/sys/bus/`, `/sys/devices/` all reflect real device/driver structure rather than being an arbitrary namespace. In short: `/proc` for processes and general kernel info (with a historical grab-bag element), `/sys` for a structured view of hardware/drivers.
_What the interviewer is probing for:_ Specific, structural understanding rather than "they're both kernel filesystems" — and awareness that overlapping info sometimes exists in both due to historical accident, not clean design.

**🎯 Senior:** _"A teammate ran `sysctl -w net.ipv4.ip_forward=1` to fix a routing issue, and it worked — until the host rebooted during scheduled maintenance and the issue came back. What happened, and how do you prevent it?"_
**Model answer:** `sysctl -w` (and an equivalent direct `echo 1 > /proc/sys/net/ipv4/ip_forward`) only changes the currently running kernel's in-memory parameter value — it never touches any config file, so there's nothing for the next boot to reapply. The fix needs to exist in two places: the runtime change (already applied, so no immediate action needed) and a persistent entry in `/etc/sysctl.d/`, e.g. a file containing `net.ipv4.ip_forward = 1`, which gets applied automatically at boot and can also be reloaded immediately with `sysctl -p` to confirm it takes effect without waiting for the next reboot. I'd also want this captured in configuration management rather than a manual file edit, so it survives host replacement, not just reboot.
_What the interviewer is probing for:_ Correctly diagnosing the runtime-vs-persistent distinction as the root cause, not just "reapply the sysctl -w command," and thinking about durability beyond a single host's local config file.

**🎯 Architect:** _"You're building an automated fleet-health check that needs to detect, without SSH-ing in interactively, whether disks are SSD or spinning, what network interfaces are up, and whether a specific security-relevant sysctl parameter is set correctly across hundreds of hosts. How do you approach this using /proc and /sys, and what are the tradeoffs versus using higher-level tools?"_
**Model answer:** All three checks map directly onto files under `/sys` and `/proc/sys` that can be read with nothing more than `cat`, no privileged tooling or parsing of command output required: `/sys/block/<dev>/queue/rotational` for SSD-vs-spinning per block device, `/sys/class/net/<iface>/operstate` for interface up/down state, and `cat /proc/sys/<param.path>` (or `sysctl <param>`) for the security parameter, comparing against the expected value. The advantage of reading these directly over parsing `lsblk`, `ip link`, or `sysctl -a` output is that they're stable, structured, single-value files — trivially scriptable via SSH/Ansible/whatever orchestration tool the fleet uses, with no output-format parsing fragility across tool versions or locales. The tradeoff is that higher-level tools (`lsblk -o`, `nmcli`, dedicated fleet-audit agents) often present richer context in one call and handle edge cases like device renaming or missing files more gracefully — for a small number of targeted, well-known checks running at fleet scale, though, reading the specific `/sys`/`/proc` file directly is faster, more portable across distros, and has fewer external dependencies than shelling out to a higher-level tool per host per check.
_What the interviewer is probing for:_ Practical fluency in using `/proc`/`/sys` directly as a scripting primitive at scale, and judgment about when direct-file reads are the right tool versus when a higher-level abstraction earns its overhead.

## 8. Key Takeaways

- `/proc` and `/sys` are pseudo-filesystems with no disk backing — every file's content is generated by the kernel on read from live in-memory state, nothing persists across reboots, and both are mounted and used through the same VFS-mediated tool interface as any real filesystem.
- `/proc` centers on per-process info (`/proc/[pid]/status`, `cmdline`, `fd/`, `maps`, `environ`) and general system state (`cpuinfo`, `meminfo`, `loadavg`, `mounts`); `/proc/[pid]/fd/` in particular is the fast, no-extra-tooling way to see what a running process has open.
- `/sys` centers on the device and driver model — `/sys/class/net/`, `/sys/block/`, `/sys/bus/`, `/sys/devices/` — with a structure deliberately mirroring the kernel's internal object hierarchy, unlike `/proc`'s more loosely accumulated layout.
- `/proc/sys/` is the tunable-kernel-parameter tree, mirrored by the `sysctl` command (`sysctl -a`, `sysctl -w`) — both direct writes and `sysctl -w` are runtime-only and revert on reboot; permanent changes require `/etc/sysctl.conf` or `/etc/sysctl.d/`, applied via `sysctl -p`.
- `/proc/mounts` reflects what's actually mounted right now, distinct from `/etc/fstab`'s static "what should mount at boot" configuration (§20) — the two can legitimately diverge.
