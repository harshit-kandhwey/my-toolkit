# Section 34 (Part 8): Interview Preparation — Tiered Questions with Model Answers (Beginner → FAANG)

This section is different: it's a curated, cross-cutting review — the questions interviewers actually reach for when they want to probe breadth and depth at once, organized by theme instead of by section number, plus a handful of harder system-design-style questions that don't belong to any single earlier section because they require synthesizing several.

Treat this section as a rehearsal script: read a question, answer it out loud before reading the model answer, then compare.

## 2. How to Actually Prepare (Read This First)

1. **Hands-on practice beats memorization, decisively.** An interviewer can tell within thirty seconds whether you've run `git rebase -i` yourself or only read about it — the hesitations, the specific vocabulary ("it opens an editor with pick/squash/fixup lines"), and the offhand mention of a gotcha you personally hit are unfakeable. §35's labs exist precisely to generate that lived experience; do them before an interview, not just this section.
2. **Practice explaining your reasoning out loud, not just producing the right final command.** Most Git interview questions aren't really testing "do you know the flag" — they're testing whether you can narrate _why_ a specific tool is safe or unsafe in a specific situation (the Golden Rule from §14 is the canonical example). Say the reasoning aloud, even alone, before the interview. Silence while typing a command, followed by "there, done," reads as weaker than a narrated "I'm using `--force-with-lease` here instead of `--force` because it aborts if the remote moved since my last fetch."
3. **Know the object model (§5) cold, even for "just" a DevOps or SRE interview.** A disproportionate number of good discriminating questions — why commit hashes change on rebase, why Git "stores snapshots not diffs," how `git gc` and packfiles relate — resolve instantly for someone who actually understands blobs/trees/commits, and turn into memorized trivia for someone who doesn't. Interviewers know the difference.
4. **Rehearse the recovery playbook until it's reflexive.** `git reflog` → find the pre-disaster SHA → `git reset --hard` or `git switch -c` from it (§6, §15, §30) is the single most valuable sequence to have muscle memory for, because "walk me through recovering from X" is one of the most common senior-level question shapes (see the FAANG-style collaboration/recovery scenario below).
5. **Common interviewer red flags to actively avoid:**
   - Not being able to state the difference between `git fetch` and `git pull` precisely (fetch updates remote-tracking branches only, no local branch or working directory changes; pull is fetch + merge or fetch + rebase — §20).
   - Saying "Git stores diffs" as your first sentence about the object model — it's one of the most common wrong answers and an instant signal of surface-level knowledge (§5).
   - Reaching immediately for `git push --force` in any recovery scenario without mentioning `--force-with-lease` or checking who else might be affected — reads as someone who hasn't broken shared history badly enough yet to have learned caution.
   - Treating branching-strategy questions as "which one is correct" instead of "which trade-offs fit this team's constraints" (§22) — a memorized preference for Git Flow or trunk-based development, stated without qualification, is a junior tell.
   - Being unable to explain what `.git` actually contains physically (§4) — "it's just metadata" is wrong and reveals no hands-on exploration has happened.

## 3. Theme: Core Concepts & The Object Model

**[Beginner] Q1. What are the three areas in Git, and what does each command touch?**
**Model answer:** Working directory (the files you edit), index/staging area (`.git/index`, a single file recording what the next commit will contain), and the object database plus refs (`.git/objects` and `.git/refs`, the permanent, immutable history). `git add` writes a blob and updates the index; `git commit` builds tree and commit objects from the index's current content and moves the branch ref; `git checkout`/`git switch` writes both the working directory and the index from the object database. Full detail: §4.

**[Intermediate] Q2. Does Git store diffs or full snapshots, and why does this distinction matter?**
**Model answer:** Git stores complete snapshots at the logical level — every commit points, via a tree object, to the full state of every file at that commit, not a diff from the previous one. Delta compression (storing one object as a difference from a similar one) exists purely as a storage optimization inside packfiles (§7), invisible at the object model's logical level. It matters because it explains why arbitrary historical checkouts are equally fast regardless of how far back they are — there's no chain of diffs to replay to reconstruct an old version, unlike RCS's original delta-based design (§1). Full detail: §5, §7.

**[Intermediate] Q3. Why is a Git commit hash computed the way it is, and what does that make it sensitive to?**
**Model answer:** A commit's SHA is a hash of the commit object's content, which includes the root tree hash, parent commit hash(es), author/committer identity and timestamps, and the message. Because the parent hash is included, a commit's identity is inseparable from its ancestry — changing anything upstream (even a commit ten generations back) cascades new hashes down every descendant, which is exactly why rebase (§14) necessarily produces new hashes for every replayed commit, not just the ones that actually conflicted. Full detail: §5.

**[Senior] Q4. Explain the Merkle DAG structure of Git's object graph and why it gives Git its integrity guarantees.**
**Model answer:** Every object (blob, tree, commit) is named by the hash of its own content, and higher-level objects embed the hashes of the objects they reference — a tree embeds its blobs' and subtrees' hashes, a commit embeds its tree's and parents' hashes. This is a Merkle structure: any change to any object, at any depth, changes that object's hash, which changes every object that references it, all the way up to the branch tip. The practical consequence is that a branch pointer's hash is a cryptographic commitment to the entire history beneath it — you cannot tamper with any historical file, commit message, or authorship record without it being detectable as a hash mismatch somewhere in the chain, which is why Git can detect corruption (`git fsck`, §29) and why signed commits/tags (§28) only need to sign the tip to vouch for everything beneath it. Full detail: §5, §28.

## 4. Theme: Branching, Merging & Rebasing

**[Beginner] Q5. What's the difference between merge and rebase?**
**Model answer:** Merge creates a new commit with two parents, joining two lines of history together while leaving both original sequences of commits untouched — it preserves the true, branchy shape of what happened. Rebase replays one branch's commits, one at a time, on top of a different base, creating brand-new commits with new hashes and abandoning the originals, producing a linear history with no merge commit. Merge is always safe on shared branches; rebase is only safe on commits nobody else has built on top of (the Golden Rule, §14). Full detail: §13, §14.

**[Intermediate] Q6. What causes a merge conflict, mechanically, and how does Git decide when it can auto-merge versus when it needs a human?**
**Model answer:** Git performs a three-way merge using the two branch tips plus their common ancestor (merge base). For each region of a file, if only one side changed it relative to the ancestor, Git takes that side automatically — that's the vast majority of a merge, and why most merges are silent. A conflict arises only when both sides changed the _same_ region differently; Git has no way to know which change (or what combination) is intended, so it leaves conflict markers in the file and pauses for a human decision. Full detail: §13.

**[Senior] Q7. When would you deliberately choose merge over rebase for integrating a feature into `main`, even on a team that generally prefers rebase for personal branches?**
**Model answer:** Once a branch is genuinely shared — multiple people have pushed commits on top of each other on it — rebasing and force-pushing rewrites history out from under collaborators, which is the Golden Rule failure mode regardless of team preference. Separately, in contexts where the true temporal shape of history has audit or compliance value (regulated environments wanting an honest record of when parallel work actually diverged and rejoined), a merge commit's two-parent structure preserves that fact, while rebase actively erases it. The choice is a genuine trade-off, not a universal best practice — full nuance, including the Golden Rule of rebasing, in §14.

## 5. Theme: Undoing Mistakes

**[Beginner] Q8. I staged a file by mistake. How do I unstage it without losing my edits?**
**Model answer:** `git restore --staged <file>` — it reverts the index entry back to what HEAD has, but the working directory edit is completely untouched. This is distinct from `git restore <file>` (no `--staged`), which discards the _working directory_ edit and is destructive with no recovery path, since uncommitted-only content never enters the object database. Full detail: §15.

**[Intermediate] Q9. What's the difference between `git reset --soft`, `--mixed`, and `--hard`?**
**Model answer:** All three move the current branch pointer to a different commit. `--soft` leaves the index and working directory untouched relative to the old state, so the undone commit's changes land staged, ready to amend or recombine. `--mixed` (the default) also resets the index to match the new HEAD, so those changes become unstaged but remain in the working directory. `--hard` additionally overwrites the working directory, so the changes are gone from disk entirely — the only one of the three that can destroy uncommitted work that was never staged or committed. Full detail: §15.

**[Senior] Q10. `reset` and `revert` both "undo" a commit — when is each the right tool, and why does that split exist?**
**Model answer:** `reset` moves the branch pointer backward, effectively removing commits from the branch's history (they still exist, unreferenced, in the object database until garbage collected). That's a rewrite, so it requires a force-push to share and runs straight into the Golden Rule the moment anyone else has fetched those commits. `revert` creates a _new_ commit that applies the inverse diff of a target commit, leaving the original commit fully present and reachable — it's purely additive, so it's unconditionally safe on shared history, including commits already deployed to production. The rule of thumb: `reset` for local, not-yet-shared mistakes; `revert` for anything already pushed and potentially depended on. Full detail: §15.

## 6. Theme: Collaboration, Remotes & Recovery (FAANG-Style Scenario)

**[FAANG-style, Scenario] Q11. A teammate force-pushed over shared history on a feature branch. Five people now have confused or broken local state. Walk me through the recovery.**
**Model answer:** First, stop anyone from making the situation worse — tell the team not to force-push anything else on that branch until this is resolved, and not to run `git pull` naively (which can create a confusing merge of unrelated-looking histories, per the Golden Rule in §14). Second, establish ground truth: find the pre-force-push tip. The most reliable source is each affected developer's own `git reflog` — it records every position `HEAD` and branch refs have held locally on that machine, including the commit the branch pointed to right before their last fetch/pull picked up the rewritten history (`git reflog show <branch>` or `git reflog show origin/<branch>` depending on where the old state is recorded). Anyone who fetched before the force-push likely still has the old tip reachable in their reflog or as a local branch. Third, reconstruct: from whichever developer has the most complete pre-force-push state, create a recovery branch at that commit (`git branch recovery-branch <old-sha>`) so it's pinned and won't be garbage collected. Fourth, reconcile the two histories deliberately rather than mechanically: diff the old tip against the new force-pushed tip to see exactly what the force-push discarded (`git log old-tip..new-tip` and the reverse), identify which commits from the old line are genuinely missing from the new one, and cherry-pick (§17) those specific commits onto the current branch tip — this preserves the intended new history while recovering lost work, rather than blindly reverting the force-push and losing whatever legitimate reason it happened for. Fifth, once reconciled, everyone else resets their local branch to match the agreed-upon new tip (`git fetch && git reset --hard origin/<branch>`) after confirming they have no uncommitted local work of their own at risk. Finally, prevent recurrence: adopt `--force-with-lease` as the required force-push form (it refuses if the remote moved since your last fetch, catching exactly this scenario before it happens) and consider branch protection rules (§23) that block force-push entirely on shared branches. The core insight the interviewer is listening for: nothing is usually actually gone — reflog entries and unreferenced-but-not-yet-GC'd objects are the safety net — but recovery requires methodically reconstructing intent, not just reverting mechanically. Full grounding: §6 (reflog), §14 (Golden Rule), §17 (cherry-pick), §29-§30 (maintenance/disaster recovery).

**[FAANG-style, System Design] Q12. Design a branching strategy for a team of 200 engineers shipping daily.**
**Model answer:** At 200 engineers shipping daily, the two dominant constraints are: integration must happen continuously (long-lived divergent branches at this scale guarantee brutal merge conflicts) and `main` must always be deployable, since "daily" implies frequent, low-ceremony releases rather than scheduled stabilization windows. This points toward **trunk-based development** (§22) rather than Git Flow: a single long-lived `main`, short-lived feature branches (ideally living hours to a couple of days, not weeks), and small, frequent merges. Concretely: (1) every change lands via a short branch and a PR with mandatory review and required CI checks (§21, §23's branch protection) before merge; (2) incomplete features that must span multiple days are shipped behind **feature flags** rather than long-lived branches, decoupling "merged to main" from "visible to users" — this is what actually makes daily shipping compatible with large, multi-day features, and is the piece teams new to trunk-based development most often miss; (3) `main` merges use squash-and-merge or rebase-and-merge (§14) to keep history readable at this commit volume, with a strict CI gate (build, tests, linting) blocking any merge that would break `main`'s deployability guarantee; (4) at 200 engineers, some path-based ownership is needed — CODEOWNERS (§23) routes review load sensibly rather than everyone reviewing everything; (5) releases are cut by tagging (§18) specific commits on `main` using CalVer or SemVer depending on the product, not by maintaining a separate long-lived release branch, unless the product genuinely needs to support multiple concurrent production versions (e.g., an on-prem enterprise product with LTS obligations), in which case a lightweight `release/*` branch per supported version is layered on top, cherry-picking specific fixes rather than reviving full Git Flow. The interviewer is probing whether you default to Git Flow out of familiarity or actually reason from the stated constraints (daily shipping, large team, continuous integration pressure) to trunk-based development plus feature flags as the fit. Full grounding: §22, §23, §21.

**[FAANG-style, System Design] Q13. How would you migrate a 10-year-old, 50 GB monorepo to improve clone times without losing history?**
**Model answer:** First, diagnose _where_ the 50 GB actually lives before choosing a fix — `git count-objects -v` and tools that break down object size by type and path (e.g., `git-sizer`, or walking packfile contents) usually reveal that a disproportionate share is large binary blobs (build artifacts, images, vendored dependencies accidentally committed) rather than genuinely large source-code history. That diagnosis drives the strategy, because "improve clone times" and "don't lose history" are in tension only if approached wrong. Options in order of preference: (1) if the bulk is large binaries that don't need full history depth for daily work, migrate them to **Git LFS** (§26) going forward, and optionally rewrite history with `git filter-repo` (§28, §32) to move historical large-file versions to LFS too — history is preserved (LFS pointers replace blobs, the pointer objects still chain through the same commit history) while clone size drops dramatically; this does rewrite commit hashes, so it requires the same coordinated, scheduled cutover as any history rewrite (all clones must be replaced, not incrementally merged); (2) regardless of LFS, adopt **partial clone and sparse-checkout** (§26) as the default clone method going forward — nobody needs to download every blob for every historical commit just to work on today's code; a partial clone fetches commit and tree metadata eagerly but blob content lazily, on demand, which alone can turn a 50 GB full clone into a shallow multi-hundred-MB working setup for most engineers; (3) for CI specifically, shallow clones (`--depth`, §26) sidestep the history-depth cost entirely since most CI jobs only need the tip; (4) if genuinely dead history exists (old branches merged and abandoned years ago, defunct sub-projects), `git filter-repo` can also prune paths that are no longer relevant — but this is the one step that's a genuine trade-off against "don't lose history," so it needs explicit stakeholder sign-off, and even then the _old_ full history remains recoverable from backups/pre-migration mirrors rather than truly destroyed. Critically, "don't lose history" and "small clone" aren't actually in conflict for options (2) and (3) — sparse/shallow/partial clone don't delete anything from the canonical repository, they just stop _transferring_ what a given clone doesn't need, which is usually sufficient and requires no disruptive rewrite at all. I'd start there before ever touching `filter-repo`, and reserve history rewriting for confirmed binary bloat. Full grounding: §26, §28, §32.

**[FAANG-style, Scenario] Q14. A secret (API key) was committed and pushed weeks ago, and has since been merged into `main` and cherry-picked into three release branches. Walk me through remediation.**
**Model answer:** Two separate tracks, and the first matters more than the second: (1) **rotate the credential immediately** — treat it as compromised the moment it left a private context, regardless of whether anyone is known to have seen it, because a purge from Git history does not retroactively un-expose it to anyone who already cloned, forked, or has it cached in CI logs, and public repos in particular may already be scraped by automated credential-harvesting bots within minutes. Rotation is the only step that actually neutralizes the risk; everything else is cleanup. (2) Purge from history using `git filter-repo` (the modern, recommended tool — not the deprecated `filter-branch`), targeting the specific file or a content pattern, across every branch that carries it, including all three release branches, not just `main`. This rewrites commit hashes on every branch touched, so it requires a coordinated, scheduled operation: notify the team of a hard cutover time, force-push every rewritten branch, and have every developer re-clone or hard-reset rather than merge/pull (merging old and new histories reintroduces the purged content). Also purge any tags pointing at affected commits and invalidate cached copies where feasible — forks and any CI artifact/cache storage that might retain old blobs are outside Git's control and need separate handling. Finally, prevent recurrence: pre-commit hooks or a secret-scanning tool (§24, §28) that blocks commits matching credential patterns before they ever reach history, and mandatory secret-scanning in CI as a second layer. The interviewer is checking whether you lead with rotation (the actual security fix) rather than jumping straight to history rewriting (which alone gives false confidence, since exposure already happened). Full grounding: §28.

## 7. Theme: Internals, Performance & Scaling

**[Intermediate] Q15. Why does `git gc` matter, and what does it actually do?**
**Model answer:** Over normal use, Git accumulates **loose objects** — one file per object, written individually as you commit — plus unreferenced objects left behind by operations like `reset --hard` or amended/rebased commits. `git gc` consolidates loose objects into compact, delta-compressed **packfiles** (§7), which are both smaller on disk and faster to transfer over the network, and prunes objects that are unreachable from any ref and older than the safety grace period (default two weeks), which is what actually frees disk space from abandoned commits. It's largely automatic (Git runs it opportunistically after operations that create enough loose objects), but very large or very active repos benefit from explicit scheduled maintenance. Full detail: §7, §29.

**[Senior] Q16. A `git status` that takes ten seconds on a monorepo with two million files — what's actually slow, and what are the fixes?**
**Model answer:** `git status` has to determine which tracked files changed, and the naive path is stat-ing every single tracked file to compare size/mtime against what the index recorded, then falling back to full content hashing when the fast metadata check is ambiguous — at two million files, that stat storm dominates. Fixes, roughly in order of impact: enable `core.fsmonitor` (Watchman or Git's built-in FSMonitor), which maintains a live watch on the filesystem and tells Git exactly which paths changed since the last check, skipping the full stat scan entirely; adopt **sparse-checkout** so a given engineer's working directory only materializes the subset of the repo they actually work in, shrinking the scan surface directly; ensure the untracked-cache and split-index features are enabled, both of which reduce redundant work across invocations. At the most extreme end, this is exactly the pressure that pushed Google to Piper and Meta to Sapling/EdenFS (§1) rather than stretching plain Git further — worth mentioning as the ceiling this optimization path eventually hits. Full detail: §4, §26.

## 8. Theme: Security & Enterprise Practice

**[Intermediate] Q17. What does commit signing actually protect against, and what does it not protect against?**
**Model answer:** A signed commit or tag (GPG or SSH signing) proves that the private key holder vouches for that exact object's content — since the signature covers the object's hash, and the hash covers the full content including parentage, signing the tip of a branch cryptographically attests to everything beneath it via the Merkle structure. What it does _not_ protect against: it doesn't stop someone from committing malicious code under their own honestly-signed identity, it doesn't verify the _author_ field (which is just text anyone can set) independent of the _signer_, and an unsigned or wrongly-configured remote can still accept unsigned commits unless server-side policy enforces signing. It's an integrity and non-repudiation control, not a code-review substitute. Full detail: §28.

**[Senior] Q18. Your organization requires SOC 2 compliance and wants every merge to `main` traceable to an approved, reviewed pull request with no possibility of a direct unreviewed push. How do you enforce this with Git and hosting-platform features, and where are the actual enforcement boundaries?**
**Model answer:** Git itself has no concept of "approval" — that layer is enforced entirely by the hosting platform, not by core Git, which is a distinction worth stating explicitly since it's a common confusion. Enforcement: branch protection rules (§23) on `main` requiring at least N approving reviews, requiring status checks (CI) to pass, and disabling direct pushes (including for admins, if the platform supports it, since an "admin bypass" is exactly the gap an auditor will flag) forces every change through a pull request. CODEOWNERS (§23) ensures the _right_ reviewers are required for sensitive paths. Commit signing (§28) adds cryptographic non-repudiation on top — proving which key produced each commit, useful when "who actually wrote this" needs to survive a compromised or shared account scenario. The genuine enforcement boundary: branch protection is a platform-database setting, not a Git-repository property — cloning the repo elsewhere, or an admin with sufficient platform permissions, can bypass it, so the audit trail's actual root of trust is the hosting platform's own access logs and configuration history, not Git's object model. I'd flag this boundary explicitly to an auditor rather than overstate what Git alone guarantees. Full grounding: §23, §28.
