# Section 92 (Part 13): Secrets in State: Risks and Mitigations

## 1. Definition

**Plain language:** Terraform's state file is a complete record of every attribute of every resource it manages — and that record is stored in plain, readable text (JSON) by default. If a database password, API key, or TLS private key ever passes through a resource argument (even one you carefully marked `sensitive` in your configuration), that value is written into the state file in full, recoverable form. Marking a variable `sensitive` hides it from your terminal; it does nothing to the state file.

**Precise definition:** **Secrets in state** refers to the class of risk created by Terraform's core architectural requirement to persist the full attribute set of every managed resource — including any attribute whose value is a credential, key, token, or other confidential data — in the state file, in plaintext, regardless of whether that value's source variable or output was declared `sensitive = true`. The `sensitive` flag is a **display-layer control**: it redacts values from CLI output (`plan`, `apply`, `output`) and from logs generated by those commands. It provides **zero protection** for the state file itself, which remains a JSON document containing every resource attribute unencrypted at rest unless the **backend** storing it independently provides encryption ([§98](./Section-98-Part13-Secure-Backend-Configuration-Encryption-Access-Controls.md)) and access control.

> 💡 **Tip:** Treat `terraform.tfstate` as if it were a file containing every secret your configuration ever touched — because, structurally, it does. The question to ask about any secret-bearing resource is never "did I mark this sensitive?" but "who and what can read the state file this ends up in, and is that state file encrypted at rest?"

## 2. Why This Matters

- **This is the single most misunderstood fact in Terraform security.** Engineers routinely mark a `db_password` variable `sensitive` and conclude the secret is now "protected" by Terraform — it is not; it is protected only from appearing in console output.
- **State is retrieved, copied, and cached in many places**: local disk during `plan`/`apply`, CI/CD job artifacts and logs, remote backend storage, and any teammate's machine that ran `terraform state pull`. Every one of those locations now holds a plaintext secret.
- **Resources frequently generate or receive secrets as ordinary attributes** — an `aws_db_instance` password, an `azurerm_key_vault_secret` value written via Terraform itself, an `random_password` resource's `result` attribute — with no way to opt a specific attribute out of state storage.
- **A leaked state file is equivalent to a leaked secrets vault.** Incident response for an exposed `.tfstate` file (committed to a public repo, an unencrypted S3 bucket left public) must assume every credential referenced anywhere in that configuration is compromised and needs rotation.
- **Compliance frameworks care about this specifically.** SOC 2, PCI-DSS, and similar audits routinely ask where Terraform state lives, whether it's encrypted, and who can read it — because auditors know state is a de facto secrets store.

## 4. Architecture / Conceptual Diagram

```text
   WHAT "sensitive = true" ACTUALLY PROTECTS (and doesn't)

   variable "db_password" {
     type      = string
     sensitive = true
   }
                │
                ▼
   ┌─────────────────────────────────┐        ┌──────────────────────────────┐
   │   CLI / Log Output              │        │   terraform.tfstate (JSON)   │
   │   $ terraform plan              │        │                              │
   │   # aws_db_instance.main        │        │  "password": "Sup3rS3cr3t!", │
   │   ~ password = (sensitive value)│        │  "arn": "arn:aws:rds:...",   │
   │                                 │        │  ... every other attribute   │
   │   REDACTED ✅                  │        │  PLAINTEXT ❌                │
   └─────────────────────────────────┘        └──────────────────────────────┘
                                                          │
                                    ┌─────────────────────┼─────────────────────┐
                                    ▼                     ▼                     ▼
                              Local disk           CI/CD job cache      Remote backend
                              (laptop, .gitignore    (unless purged      (S3/Storage/GCS —
                              can fail to catch it)   after run)         needs SSE + IAM,
                                                                          §98)

   The ONLY layers that actually protect the plaintext secret in state:
   1. Backend encryption at rest (§98)
   2. Backend access control / IAM (§98, §95)
   3. Not putting the secret in state at all (external secrets manager, §93/§94)
```

- The `sensitive` flag operates entirely at the **UI/output layer** of Terraform core — it never reaches the state serialization code path.
- The state file's JSON structure ([§47](../Part7/Section-47-Part7-The-State-File-Format-terraform-tfstate-Deep-Dive.md)) stores the **post-apply value of every attribute**, sensitive or not, because Terraform needs the full attribute set to compute future diffs — there is no mechanism to selectively omit one attribute from persistence while still tracking the resource.
- Real protection is layered: encrypt the backend, restrict who can read it, and — the strongest mitigation — avoid ever letting Terraform manage the _raw secret value_ in the first place by delegating secret generation/storage to Vault or a cloud-native secrets manager and referencing it by reference (a Vault path, a Secrets Manager ARN) rather than by value.

## 5. Hands-On

### 5.1 Demonstrating the Gap Between `sensitive` and State Protection

**Purpose:** Prove concretely that a `sensitive`-flagged value is fully readable in state despite being redacted from CLI output.

**Syntax:**

```hcl
variable "db_password" {
  type      = string
  sensitive = true
}

resource "aws_db_instance" "main" {
  identifier = "app-db"
  engine     = "postgres"
  username   = "app"
  password   = var.db_password
  # ... other required arguments omitted for brevity
}
```

**Example usage and expected output:**

```bash
$ terraform apply -var="db_password=Sup3rS3cr3t!"
  # aws_db_instance.main will be created
  + password = (sensitive value)
Apply complete! Resources: 1 added, 0 changed, 0 destroyed.

$ terraform state show aws_db_instance.main
# password = "Sup3rS3cr3t!"     <-- plaintext, right there

$ grep -o '"password":"[^"]*"' terraform.tfstate
"password":"Sup3rS3cr3t!"       <-- plaintext in the raw JSON too
```

**Production usage example:** This exact pattern — a `sensitive` RDS password variable — is one of the most common findings in Terraform security audits: the team believed `sensitive = true` was a control, and it isn't one for anything beyond terminal/log redaction.

**Common errors:** Assuming `terraform state show` or a raw `grep` of the state file will also redact sensitive attributes — it will not; `sensitive` is a plan/apply/output rendering concern only, not a state storage concern.

### 5.2 Reducing Exposure with `random_password` + External Secret Storage

**Purpose:** Show a pattern that avoids putting the raw secret in the configuration's variable inputs at all, generating it inside Terraform but immediately handing it to a secrets manager rather than referencing it directly elsewhere.

**Syntax:**

```hcl
resource "random_password" "db" {
  length  = 24
  special = true
}

resource "aws_secretsmanager_secret" "db_password" {
  name = "app/db-password"
}

resource "aws_secretsmanager_secret_version" "db_password" {
  secret_id     = aws_secretsmanager_secret.db_password.id
  secret_string = random_password.db.result
}

resource "aws_db_instance" "main" {
  identifier = "app-db"
  password   = random_password.db.result
  # ...
}
```

**Example usage and expected output:**

```bash
$ terraform apply
  # random_password.db will be created
  # aws_secretsmanager_secret.db_password will be created
  # aws_secretsmanager_secret_version.db_password will be created
  # aws_db_instance.main will be created
Apply complete! Resources: 4 added, 0 changed, 0 destroyed.
```

**Production usage example:** Even here, `random_password.db.result` and the RDS `password` attribute both still land in state plaintext — this pattern does NOT solve the state-exposure problem, it only ensures the secret is _also_ durably stored in a proper secrets manager for application consumption. The state-exposure problem is only fully solved by encrypting/restricting the backend ([§98](./Section-98-Part13-Secure-Backend-Configuration-Encryption-Access-Controls.md)) or by never letting Terraform generate/hold the raw value at all ([§93](./Section-93-Part13-Integrating-HashiCorp-Vault-with-Terraform.md), [§94](./Section-94-Part13-Cloud-Native-Secrets-Managers-AWS-Azure-GCP.md)).

**Common errors:** Believing that writing a secret into Secrets Manager "removes" it from state — it does not; state still records the value that was written, because Terraform must track what it set in order to detect drift on future plans.

## 6. Production Usage Notes

- **There is no supported way to exclude a single attribute from state serialization.** Terraform must persist every attribute of every managed resource to compute accurate diffs; partial persistence would break the plan engine's ability to detect drift on that attribute.
- **`ephemeral` values and write-only arguments (introduced in newer Terraform versions for select resources) are the closest thing to a real fix** — some providers now support write-only attributes that are used at apply time but never persisted to state. As of this writing this coverage is provider- and resource-specific, not universal; verify per-resource-per-provider before relying on it.
- **State files must never be committed to version control.** This sounds obvious but remains one of the most common real-world incidents — a local backend's `terraform.tfstate` accidentally added via `git add .` and pushed to a shared (or public) repository.
- **`terraform state pull` output is just as sensitive as the backend file itself** — anyone who can run this command against your backend can read every secret in state, so access to run Terraform commands against a given state IS access to its secrets.

## 7. Security Considerations

- **The core hard truth, stated precisely: Terraform state stores the full plaintext value of every resource attribute, including attributes sourced from `sensitive`-flagged variables or producing `sensitive`-flagged outputs.** The `sensitive` mechanism redacts CLI/log output only; it has no effect whatsoever on what is written into the state file's JSON body. Any engineer, auditor, or interview candidate who states otherwise has a materially wrong security model of Terraform.
- **State backups compound the exposure.** Many backends (S3 versioning, Terraform Cloud state history) retain prior versions of state — a secret rotated out of the _current_ state may still be readable in an older _version_ of the state file unless backup retention and encryption are also addressed.
- **Local state on a developer laptop is frequently the weakest link** — unmanaged, unencrypted-at-rest by default (depending on disk encryption), synced to personal cloud backup tools, and outside any centralized access-control or audit trail. Remote backends ([§48](../Part7/Section-48-Part7-Local-State-vs.-Remote-State.md), [§49](../Part7/Section-49-Part7-Remote-Backends-Overview-S3-Azure-Storage-GCS-TFC.md)) exist partly as a security control, not just a collaboration one.
- **`terraform plan -out=tfplan` binary plan files also embed the full resource values**, including secrets — a saved plan file handed off to a CI runner or reviewer is exactly as sensitive as the state file itself and must be handled (and cleaned up) accordingly.
- **The strongest mitigation is architectural, not procedural**: prefer designs where Terraform never handles the raw secret value at all — it references a secret by ARN/path/URI (Vault, [§93](./Section-93-Part13-Integrating-HashiCorp-Vault-with-Terraform.md); cloud-native managers, [§94](./Section-94-Part13-Cloud-Native-Secrets-Managers-AWS-Azure-GCP.md)) and the _consuming application_ fetches the value at runtime, out of band from Terraform entirely.

## 8. Common Troubleshooting Scenarios

| Symptom                                                                     | Likely Cause                                                                            | Resolution Path                                                                                                                                                                                                         |
| --------------------------------------------------------------------------- | --------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Secret found in plaintext in `terraform.tfstate` despite `sensitive = true` | Misunderstanding of what `sensitive` protects — it is display-only, not storage-level   | Rotate the exposed secret immediately; move to encrypted remote backend with restricted IAM ([§98](./Section-98-Part13-Secure-Backend-Configuration-Encryption-Access-Controls.md)); consider external secret reference |
| State file accidentally committed to Git history                            | Local backend used without `.gitignore` entry, or `git add .` swept it up               | Rotate every secret referenced in the leaked state; purge the file from Git history (e.g. `git filter-repo`); migrate to remote backend                                                                                 |
| CI/CD pipeline logs show a secret was in a cached plan artifact             | Saved plan file (`-out`) treated as a non-sensitive build artifact and retained/exposed | Treat plan files as secret-bearing; restrict artifact retention/visibility; delete after run; avoid uploading plan files to shared/public storage                                                                       |
| Old (rotated) secret still readable via backend version history             | Backend versioning/backup retains prior plaintext state versions after rotation         | Apply retention policies to state version history; ensure encryption at rest covers historical versions too ([§98](./Section-98-Part13-Secure-Backend-Configuration-Encryption-Access-Controls.md))                     |

## 9. Best Practices

- Always pair `sensitive = true` with remote, encrypted, access-controlled backend storage ([§98](./Section-98-Part13-Secure-Backend-Configuration-Encryption-Access-Controls.md)) — one without the other is an incomplete control.
- Prefer external secret references (Vault dynamic secrets, [§93](./Section-93-Part13-Integrating-HashiCorp-Vault-with-Terraform.md); cloud-native secret ARNs consumed at runtime by the application, [§94](./Section-94-Part13-Cloud-Native-Secrets-Managers-AWS-Azure-GCP.md)) over letting Terraform generate or pass raw secret values through resource arguments whenever the target resource/provider supports it.
- Where write-only/ephemeral attribute support exists for a given resource, use it in preference to a standard argument for secret material.
- Restrict `terraform state pull`, `state show`, and backend read access to the same principals who would otherwise have direct access to the underlying secrets — state read access is secret read access.
- Include state file exposure explicitly in incident-response runbooks: a leaked `.tfstate` should trigger the same rotation workflow as a leaked credentials file.

## 10. Common Anti-Patterns / Mistakes

- **Treating `sensitive = true` as sufficient protection and stopping there.** It is a UX control against shoulder-surfing terminal output and accidental log capture, not a security boundary.
- **Storing local state on a shared filesystem or laptop "temporarily" for a production environment.** Temporary local state for production infrastructure routinely becomes permanent, unencrypted, and unaudited.
- **Passing raw secrets as plain (non-sensitive) variables** — an easy audit finding, since it means the value also leaks into `plan`/`apply` console output in addition to state.
- **Assuming secret rotation "removes" the old value from history.** Old state versions in backend backup/versioning can retain the pre-rotation secret unless those historical versions are also purged or were never persisted.

## 11. Interview Questions

**🎯 Beginner:** _"If I mark a Terraform variable `sensitive = true`, is the value it holds encrypted?"_
**Model answer:** No. `sensitive = true` only suppresses the value from being printed in `plan`/`apply`/`output` CLI output and associated logs. The value is still written in full plaintext into the Terraform state file. Encryption of that value depends entirely on whether the backend storing the state file provides encryption at rest, which is a separate, unrelated configuration.
_What the interviewer is probing for:_ Whether the candidate has the single most important — and most commonly wrong — fact about Terraform security correct.

**🎯 Intermediate:** _"Where can a secret that only ever appeared in a `sensitive` variable end up, beyond the state file?"_
**Model answer:** The state file itself (plaintext), any saved plan file (`-out`), local disk copies during apply, CI/CD job caches or artifacts if the plan/state isn't cleaned up, any backend version history/backups, and anywhere `terraform state pull` output is captured or logged. Because `sensitive` doesn't touch storage, every one of these persistence points holds the raw value.
_What the interviewer is probing for:_ Breadth of understanding of state's footprint beyond "the state file on the backend," including CI artifacts and version history, which are frequently overlooked.

**🎯 Senior:** _"A teammate proposes fixing secret exposure by encrypting `terraform.tfstate` with a script after every apply. What's wrong with that approach, and what should be done instead?"_
**Model answer:** Post-hoc encryption of a local file after the fact leaves a window where the plaintext state exists on disk (and possibly already synced/backed up) before the script runs, doesn't protect intermediate copies (plan files, CI caches), and is fragile — a failed or skipped script run silently leaves plaintext state. The correct approach is to use a remote backend that provides encryption at rest natively and atomically as part of every write (S3 with SSE, Azure Storage encryption, GCS default encryption — [§98](./Section-98-Part13-Secure-Backend-Configuration-Encryption-Access-Controls.md)), combined with IAM/access controls restricting who can read the backend at all, and ideally reducing how many real secrets ever reach state in the first place via external secret references ([§93](./Section-93-Part13-Integrating-HashiCorp-Vault-with-Terraform.md), [§94](./Section-94-Part13-Cloud-Native-Secrets-Managers-AWS-Azure-GCP.md)).
_What the interviewer is probing for:_ Understanding that the fix belongs at the backend/architecture layer, not as a bolt-on script, and awareness of the multiple plaintext copies a naive fix would miss.

**🎯 Architect:** _"Design a Terraform secrets-handling strategy for an organization that must satisfy a compliance auditor asking 'prove no plaintext secret material can be exfiltrated by a single compromised credential.'"_
**Model answer:** Layer the mitigations: (1) minimize what Terraform ever holds — favor Vault dynamic, short-lived credentials ([§93](./Section-93-Part13-Integrating-HashiCorp-Vault-with-Terraform.md)) or cloud-native secret references ([§94](./Section-94-Part13-Cloud-Native-Secrets-Managers-AWS-Azure-GCP.md)) over static secrets passed as variables, so the state file at most contains references/leases, not long-lived plaintext; (2) encrypt the backend at rest and enforce TLS in transit ([§98](./Section-98-Part13-Secure-Backend-Configuration-Encryption-Access-Controls.md)); (3) apply least-privilege IAM so the Terraform execution role's own credentials ([§95](./Section-95-Part13-Least-Privilege-IAM-for-Terraform-Execution-Roles.md)) are scoped narrowly, and separately scope who can read the state backend, ideally requiring a different principal/approval path than who can run applies; (4) enable backend access logging/audit trails so state reads are attributable to a principal, not just possible; (5) apply the same encryption/retention discipline to plan files and CI artifacts, not just the state file itself; (6) build secret rotation into the incident-response runbook explicitly triggered by any suspected state exposure. No single control satisfies "no single compromised credential" — it requires that reading state, running applies, and reading the underlying secrets manager are gated by distinct, least-privileged principals so no one compromised credential spans all three.
_What the interviewer is probing for:_ Systems-level thinking about defense in depth rather than a single silver-bullet answer, and explicit reasoning about the "single compromised credential" blast-radius framing.

## 12. Common Misconceptions

1. **"`sensitive = true` encrypts or hides the value from the state file."** It affects CLI/log output only; the state file's plaintext content is entirely unaffected.
2. **"If I never print the secret with `terraform output`, it's safe."** The secret is in the state file regardless of whether any output block ever surfaces it — state stores every resource attribute, not just outputs.
3. **"Remote backends are inherently encrypted."** Remote backend storage capability (S3, Azure Storage, GCS) supports encryption at rest, but it is a configuration you must explicitly enable and correctly apply ([§98](./Section-98-Part13-Secure-Backend-Configuration-Encryption-Access-Controls.md)) — it is not automatic by merely using a remote backend instead of local state.
4. **"Rotating a secret removes it from Terraform's history."** Rotation changes the _current_ state's value going forward; prior state versions retained by backend versioning/backups may still contain the old plaintext value unless separately purged.

## 13. 🔑 Key Takeaways

- Terraform state stores the full plaintext value of every managed resource attribute — including anything sourced from a `sensitive`-flagged variable — by design, because the plan engine needs the complete attribute set to compute diffs.
- The `sensitive` flag is a display/output redaction control (CLI, logs) only; it has no effect on state file content.
- Real protection requires backend-level controls: encryption at rest, transport encryption, and least-privilege access control over who can read the backend ([§98](./Section-98-Part13-Secure-Backend-Configuration-Encryption-Access-Controls.md)) — plus, where possible, reducing what secret material Terraform ever handles via Vault or cloud-native secrets managers ([§93](./Section-93-Part13-Integrating-HashiCorp-Vault-with-Terraform.md), [§94](./Section-94-Part13-Cloud-Native-Secrets-Managers-AWS-Azure-GCP.md)).
- Saved plan files and backend version history/backups carry the same exposure risk as the live state file and need the same handling.
- Any suspected state file exposure should trigger rotation of every secret referenced in that state, not just a config fix.
